sql_state — What SQL knowledge can the explanation assume?

assumed

The reader can read SELECT, UPDATE, WHERE and recognize table rows and column values. No transaction or concurrency-control vocabulary is assumed.

Evidence

    correctness — What makes a database operation correct for an application?

    supported

    The application has a rule that should hold in completed states: for example, a transfer preserves the combined account balance. Such a rule is often called an invariant. An operation is correct in isolation when, starting from a state satisfying the rule, its complete execution leaves the rule satisfied. Valid SQL alone does not establish that property.

    transaction — What operations belong to a transaction, and what do commit and rollback mean?

    supported

    A transaction groups SQL work into one completion unit. BEGIN starts an explicit group; COMMIT retains its work; ROLLBACK discards it. A connection is an application conversation with the database, and separate connections can run separate transactions. PostgreSQL implicitly wraps a standalone statement in a transaction.

    atomicity — What does all-or-nothing completion guarantee?

    supported

    Atomicity means all updates in a transaction survive together or none do. A transfer must debit and credit together. That rule does not alone ensure that the values used to decide what to write stay appropriate while another transaction changes related data. Visibility of unfinished changes is an isolation question.

    overlap — How can two transactions overlap even when each statement executes correctly?

    supported

    Concurrent means transaction lifetimes overlap. A can read, B can read, A can write, and B can write before both finish; no physically simultaneous CPU execution is required. Each SQL statement can correctly act on its permitted inputs while those inputs omit a competing decision.

    serial — What would executing whole transactions one at a time mean?

    supported

    A serial execution completes all of A before starting B, or all of B before starting A. If each transaction preserves a rule whenever it starts from a valid state, either serial order preserves that rule. This is reasoning about complete operations, not merely the order of final writes.

    interference — How can overlapping, individually valid decisions violate a shared rule?

    supported

    Constructed example: two staff rows, A and B, initially have on_call=true; the rule requires at least one true. Each transaction reads the other row and sets its own row false only if the other is true. Either operation alone preserves the rule. If both read first, both decisions pass, then they update different rows and both can commit under PostgreSQL Repeatable Read. The result has nobody on call. The writes are correct for each transaction’s observations; the combined decision is wrong.

    visibility — Which version of a row can a read observe?

    supported

    A read observes a particular permitted state, not necessarily every latest change. Distinguish another transaction’s uncommitted work, its committed work, and this transaction’s own earlier writes. PostgreSQL ordinary SELECT sees its own preceding updates, even before commit; its view of other transactions depends on isolation level.

    anomalies — How do dirty, changed-value, changed-set, and serialization anomalies differ?

    supported

    A dirty read sees someone else’s unfinished update. A nonrepeatable read sees a previously read value change after another commit. A phantom read sees the rows satisfying the same WHERE condition change after another commit. A serialization anomaly means the committed outcome matches no ordering of complete transactions. Stable individual reads therefore do not by themselves rule out every bad combined outcome.

    snapshot — How can a read see a stable database state while another transaction writes?

    supported

    A snapshot is the database state a read is allowed to observe. Multiversion concurrency control (MVCC) keeps distinguishable versions so a read can use an earlier state while other work writes newer data. PostgreSQL Read Committed ordinary SELECT uses a new snapshot per statement; Repeatable Read uses the first non-control statement’s snapshot for the transaction, plus its own writes.

    levels — What protections do the named isolation levels promise?

    supported

    The conventional four-level comparison specifies forbidden outcomes. Read Uncommitted may allow all four anomalies; Read Committed forbids dirty reads; Repeatable Read also forbids nonrepeatable reads but its minimum guarantee can allow phantoms and serialization anomalies; Serializable forbids all four. Products can exceed these minima: PostgreSQL Read Uncommitted behaves as Read Committed, and its Repeatable Read also prevents phantoms. A level is a guarantee about allowed behavior.

    snapshot_limit — Why can a stable transaction snapshot still allow a wrong combined result?

    supported

    In the on-call example both transaction snapshots contain two available staff. Each changes a different row, so a same-row write collision need not occur. A then B would leave B on call because B reads A=false; B then A would leave A on call. Both-off fits neither order. Repeatable reads stabilize observations but do not necessarily protect the assumptions linking reads of one row to writes of another.

    serializable — What does serializable execution guarantee?

    supported

    Serializable promises that successfully committed transactions have an effect equivalent to some serial order. Actual work may overlap. If every participating operation preserves the application rule in isolation, this guarantee preserves it across their committed combination. It cannot repair logically incorrect operations or a workflow whose required reads occur outside its transaction.

    mechanisms — How do snapshots, locks, and conflict checks implement isolation?

    supported

    A mechanism is how the database enforces its promise. Snapshots choose visible versions. Blocking locks reserve access so a conflicting operation waits; protecting a searched range can also prevent new matching rows. Conflict checking instead detects combinations of reads and writes incompatible with the promised order and rejects work. PostgreSQL Serializable adds such checks to snapshots; its read-dependency tracking is not a blocking read lock. Engines can combine these techniques.

    engine_details — Why do engine and statement type matter beyond the level name?

    supported

    Do not apply ordinary SELECT rules automatically to UPDATE or locking reads. InnoDB 8.4 Repeatable Read ordinary reads share a snapshot, while locking reads/modifications protect searched records or ranges. With autocommit disabled, its Serializable level treats plain SELECT as shared locking reads. SQLite WAL supports concurrent snapshot readers but only one writer; a stale reader attempting to write can fail with SQLITE_BUSY_SNAPSHOT. Thus using snapshots does not imply that every engine permits the on-call anomaly.

    retries — Why must applications sometimes retry a whole transaction?

    supported

    A serialization failure means the attempted transaction could not be safely accepted with competing work. Discard it and retry the whole transaction, including its reads and decisions, from fresh state; replaying only its final write can repeat the invalid decision. PostgreSQL Repeatable Read can require this too. SQLite stale-snapshot rejection similarly requires releasing the old snapshot before starting again. A rejection can be how isolation protects correctness.

    choice — How should correctness requirements guide the isolation choice?

    supported

    Start with the rule and all reads and writes needed to preserve it. Choose guarantees that exclude the dangerous interleavings, using the actual engine and statement behavior. Serializable provides general serial-equivalence protection for correctly bounded transactions, with retry handling. Weaker levels may suffice for narrower operations with appropriate coordination. Waiting, rejected attempts, and performance depend on workload; no universally fastest or best level follows from these sources.

    target — Why can concurrent correct operations yield a wrong result, and how do isolation levels help?

    supported

    Two individually correct operations can base their decisions on observations that omit each other’s changes; their combined writes can then break an application rule. Transaction boundaries make work a unit, while isolation constrains what overlapping units may observe and commit. Weaker guarantees exclude particular read anomalies; even stable snapshots can permit incompatible decisions. Serializable excludes outcomes with no serial equivalent, often by waiting or rejecting work that must be retried. The engine, statements, and correctly chosen transaction boundaries determine how those guarantees apply.
