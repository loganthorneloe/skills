    coverage — Which cases should be collected?

    supported

    grader — How does an output become a measurable result?

    supported

    A grader applies an explicit rule to an actual output and its case-specific reference or criteria. Use code for precise properties such as valid structure or a required category; use a written human rubric, optionally automated by another model, for qualitative properties. Each score means only that its chosen rule was satisfied to that degree.

    run — What happens in one evaluation run?

    supported

    For each case, give the application its input and allowed context, save the generated response or action, and apply the grader with its reference information. Save the application configuration, case version, outputs, and grading results so the result can be inspected and rerun. For a conversation, retain earlier messages and intermediate function results, not just the last answer.

    aggregate — What does a dataset score say?

    supported

    For a binary criterion, divide the number of passing cases by the number graded and state both counts. Inspect separate criteria and case groups as well as the overall score. This describes performance on the cases and runs tested; it does not prove performance on all future customer conversations. Also report attempted and completed counts; incomplete cases must not disappear silently.

    comparison — How can an evaluation compare application changes?

    supported

    Run the two identified application versions on the same cases with unchanged grading rules and equivalent starting state. Compare per-case gains and regressions, not just the average; inspect repeated attempts before interpreting a small gain. Reserve unused cases for the final comparison.

    start — How would I start evaluating a customer-support assistant?

    supported

    Start with one workflow, such as refund eligibility. Use the case, coverage and reference methods to prepare a small inspectable dataset. Execute and grade it using the run method, inspect failures, then compare revisions with the improvement method. Check real action outcomes when actions are enabled, and apply the decision limits before using scores to justify release.

    target — Why do AI applications need evals, how do they work, and how can this reader start?

    supported

    Evals turn desired application behavior into repeatable evidence: cases specify situations, grading rules define what is measured, runs produce observations, and comparisons guide improvements. They are needed because variable answers and diverse situations make informal spot checks unreliable. Start with a narrowly defined support workflow and inspect both outputs and consequential actions.

    uncertainty — Why might a higher score fail to show a dependable improvement?

    supported

    A changed score can reflect different generated answers or different selected cases. Repeated attempts probe answer variation; additional representative cases probe case coverage. Neither alone guarantees future performance.

    heldout — Why reserve cases that were not used to choose the change?

    supported

    Repeatedly choosing changes that fit the same examples can favor those examples. Keep some cases out of that selection process and evaluate the selected version on them. A held-out set still needs representative inputs and valid grading.

    decision — Does a high score mean the assistant is ready for customers?

    supported

    No universal pass rate establishes readiness. Requirements determine which failures are acceptable. Inspect important failures separately: many correct policy answers cannot cancel out one unauthorized action. Evaluation evidence informs the owner’s decision; the tested cases do not cover every future situation.

    supported
