    intent — What would acceptable support behavior mean?

    supported

    Acceptable behavior means meeting requirements for the chosen support task. Specify each criterion as an observable question. Constructed examples: Is the policy answer accurate? Does the assistant request missing information instead of inventing it? Does it escalate when the stated policy requires that? Keep these separate from tone. Actual company rules must come from its owner.

    reference — How do we know what should have happened in each case?

    supported

    For each case, store the input, relevant policy or order facts, and expert-reviewed expectations. A category task can have one correct label. An answer task can instead list required facts and forbidden claims while allowing many phrasings. The reference is the information used to judge the answer; it is not automatically a script the assistant must reproduce.

    run — What happens during one evaluation run?

    supported

    Use a Python loop to load each case, call the application with its specified inputs, and save its response and any relevant conversation or action results. Record which prompt, model, settings, policy context and grader version were used. This is one run; keeping the inputs and rules reusable makes later runs comparable.

    grade — How does an output become a result?

    supported

    A grader applies a rule to an output and the case’s reference information. Code can compare exact category labels or check structured values. A human or model can assess a rubric: explicit criteria such as factual accuracy against supplied policy. Matching wording, resembling a reference and meeting a requirement are different judgments. Use the rule that measures the intended criterion.

    summary — What does a score mean?

    supported

    For a binary criterion, pass rate = passing judged cases / all judged cases. Constructed example: 16 passes among 20 judged cases is 80%, not a probability guarantee for every future customer. State the denominator, criteria, dataset and run configuration. Keep unjudged or errored cases visible rather than silently counting them as successes. The score describes the tested behavior; its relevance depends on the cases and grading.

    compare — How do we compare changes without overinterpreting scores?

    supported

    Run the original and changed application on the same version of cases and grading criteria. Compare per-case changes and subgroup results, repeat trials to see variability, and check fresh held-out cases. A small difference alone does not establish reliable improvement. Formal uncertainty estimation for close comparisons is outside this starter graph; no statistical significance claim is made.

    start — What is a small first support-assistant eval?

    supported

    Constructed starter plan: choose policy-question answering. Save a small reviewed case collection with id, question, policy excerpt, required facts, forbidden claims and scenario tag. Include ordinary answers, missing details and escalation cases. Run the application, manually grade policy accuracy and required behavior, and compute pass counts by criterion. Inspect failures; automate only checks that agree with expert review. Change one component, rerun, and inspect regressions. Add multi-turn or tool-outcome cases if those capabilities are in scope.

    target — Why do I need AI application evals, how do they work, and how do I start evaluating a customer-support assistant?

    supported

    Evals provide repeatable evidence about whether an application meets explicit needs across relevant cases despite variable outputs. Cases exercise the application; graders compare observed behavior with expectations; results reveal failures and help compare changes. Begin with one support task and a small expert-reviewed dataset, then expand with observed failures. Scores support scoped decisions, not unrestricted claims of reliability.

    repeat — Why run the same case more than once?

    supported

    A trial is one attempt at a case. Repeated attempts reveal inconsistent success that a single run hides. Report attempts and failures; repetitions do not add new kinds of customer situations.

    holdout — Why keep some cases out of day-to-day tuning?

    supported

    Repeatedly editing a prompt to fit familiar cases can improve their scores without improving new cases. Keep some cases unused during tuning and check them occasionally. If they start guiding edits, replenish the untouched set.

    slices — Why inspect groups of cases instead of only the overall score?

    supported

    Tag scenarios so a total can be separated into relevant groups. Constructed example: 18 routine successes can hide two escalation failures in an overall 18/20 result. Show each group’s denominator and failure examples; a tiny group provides limited evidence.
