    atomicity — What does all-or-nothing execution guarantee?

    supported

    Atomicity means all of a transaction’s stored changes survive together or none do. It does not determine whether a later statement sees a newer committed transaction.

    concurrency — How can transactions overlap?

    supported

    Separate connections—separate conversations between application and database—can each have an unfinished transaction. One can read, another update and commit, and the first then read or update. Overlap needs no simultaneous CPU execution.

    wrong_result — How can two individually correct transactions produce a wrong result?

    supported

    Two transactions can each read that a shared rule permits their change, then write different rows. Each choice is correct against what it read; together the committed writes can break the rule. No dirty read or partially committed transaction is necessary.

    Examples

      constructed reasoning example, not a measured database run
      given_inputs
      • Rows A and B initially both have on_call=true.
      • Rule: at least one row remains on call.
      • Each transaction reads both rows; only if the other row is true does it set its own row false.
      • Ordinary reads; separate connections; no extra locks, constraint, or third writer.
      overlap
      • A reads both true.
      • B reads both true.
      • A sets only A false.
      • B sets only B false.
      • Both commit under a policy allowing these read/write dependencies.
      result
      Both false violates the rule; each transaction alone from the initial state would preserve it.
      serial_comparison
      A then B leaves B true, because B observes A false and does not leave. B then A leaves A true. Neither serial order produces both false.
      qualification
      Illustrates PostgreSQL Repeatable Read’s possible cross-row serialization anomaly by applying documented snapshot and update rules. Not a guarantee that every engine called Repeatable Read permits this schedule.

    snapshot — What is a read snapshot?

    supported

    A read snapshot selects which stored row versions a statement may observe. A version is the row’s values from a particular update; retaining earlier versions allows a read to use earlier committed data even after newer updates exist. A transaction also sees its own prior changes. The isolation policy chooses the snapshot’s reference point.

    repeatable_read — What does PostgreSQL Repeatable Read give ordinary reads?

    levels — What do isolation levels specify?

    supported

    Minimum protections: Read Uncommitted may permit dirty reads; Read Committed forbids those but may permit nonrepeatable and phantom reads; Repeatable Read additionally forbids nonrepeatable reads, but may permit phantoms; Serializable also forbids phantoms and all serialization anomalies. Engines may provide stronger protection than these minimums.

    locks — How can a lock coordinate conflicting operations?

    supported

    A lock records a transaction’s protected access to data. An incompatible request—such as a second writer requesting an already write-locked row—must wait until the holder commits or rolls back. Some locks protect a range against inserts. A plain snapshot read need not request such conflicting access.

    mechanisms — Why is an isolation guarantee different from its implementation?

    supported

    An isolation guarantee describes allowed observations and outcomes. Implementations can select old versions, delay incompatible access with locks, or detect unsafe read/write combinations and abort an attempt. PostgreSQL Serializable adds dependency monitoring to snapshots; its monitoring locks record dependencies without blocking.

    statement_kind — Why must a plain SELECT be distinguished from a locking read or UPDATE?

    supported

    Snapshot rules for plain SELECT do not fully describe UPDATE or a read requesting a lock. In PostgreSQL Read Committed, an updater can wait for a competing writer, then apply its operation to the newer row after rechecking WHERE. InnoDB likewise distinguishes nonlocking reads from locking statements.

    engine — Why is the isolation name alone insufficient?

    supported

    The engine, isolation level, and statement kind together determine behavior. PostgreSQL treats Read Uncommitted as Read Committed and prevents Repeatable Read phantoms. InnoDB SERIALIZABLE converts ordinary SELECT to shared locking reads when autocommit is disabled. SQLite ordinarily permits one writer; its WAL snapshots can reject a stale reader’s attempted write with SQLITE_BUSY_SNAPSHOT.

    retry — What must the application do when concurrency control rejects a transaction?

    supported

    Waiting lets an existing attempt continue after another transaction finishes. A serialization failure instead rejects the attempt. PostgreSQL requires retrying the complete transaction, including reads and logic choosing SQL and values. Retrying only the final UPDATE can reuse the invalid decision. A retry may fail again.

    target — Why can individually correct operations fail together, and how do isolation levels help?

    supported

    Individually valid read-dependent changes can combine into a result that violates an application rule when transactions overlap. Atomicity groups writes; isolation constrains observations and committed outcomes. Stronger levels prevent more anomalies, but stable snapshots alone are not serializability. With correct transaction boundaries and individually correct logic, consistent use of Serializable protects the serial-equivalent result; engines enforce guarantees using versions, locks, and possible abort/retry work. Level names also require engine and statement qualifications: PostgreSQL Repeatable Read prevents phantoms beyond the standard minimum, while InnoDB distinguishes plain and locking reads.

    stable_not_serial — Why can a stable snapshot still allow a serialization anomaly?

    supported

    A stable snapshot fixes each transaction’s view; it does not force other transactions’ decisions to agree with a single serial order. Transactions can read overlapping data, change different rows, and both commit. PostgreSQL Repeatable Read allows such outcomes; Serializable additionally checks the conflicting read/write dependencies.

    correctness_limit — When does serializable isolation preserve an application rule?

    supported

    Start from a state satisfying the rule, include each complete read/decision/write operation in one transaction, and make every relevant transaction preserve the rule when executed serially under the same guarantee. A serial-equivalent committed outcome then preserves it. Isolation does not invent the rule or repair logic that is wrong even when run alone.
