concurrency — What does concurrent execution mean?

supported

A connection is one client’s conversation with the database. Two connections can each have a transaction in progress: one reads, the other writes and commits, then the first reads again. Concurrency means these transaction lifetimes overlap; CPU instructions need not execute at exactly the same instant.

dependency — Why can a read affect the correctness of a later write?

supported

An application may read balances, decide whether a withdrawal is allowed, then update one balance. The decision relies on everything read, including rows it does not update. A concurrent change to those other rows can invalidate the decision.

snapshot — What does reading a snapshot mean?

supported

A snapshot fixes which committed row versions a read can see. Later commits can remain outside that view. PostgreSQL also lets a transaction read its own earlier writes. The snapshot’s duration depends on the isolation level; it is not automatically the whole transaction.

anomaly — How can two individually valid transactions produce an invalid combined result?

supported

If each decision relies on data the other transaction changes, both can pass a check based on older values and then commit changes to different rows. The combined result can violate a rule that either serial ordering would preserve.

levels — How do the four named isolation levels compare?

supported

At the standard minimum: Read Uncommitted permits dirty reads; Read Committed forbids them but permits changed rereads and matching sets; Repeatable Read also forbids changed rereads but may permit phantoms; Serializable forbids all three and serialization anomalies. PostgreSQL Read Uncommitted behaves as Read Committed, and its Repeatable Read also prevents phantoms. Engine names therefore matter.

read_committed — What does PostgreSQL Read Committed guarantee for ordinary SELECT?

supported

Each ordinary SELECT reads a snapshot taken at that statement’s start. It avoids dirty reads, but consecutive SELECT statements can see different committed data. PostgreSQL UPDATE is different: after waiting for a concurrent writer, it can recheck its condition against that writer’s updated row.

repeatable_read — What does PostgreSQL Repeatable Read add?

supported

Ordinary reads use the snapshot established by the first non-control statement, plus the transaction’s own writes. PostgreSQL prevents phantoms here, but serialization anomalies remain possible. An update of a row changed since the snapshot can fail and require a whole-transaction retry.

mechanisms — How can databases enforce isolation guarantees?

supported

Implementations can retain versions for snapshot reads, block conflicting operations with locks, or detect unsafe read/write dependencies and reject a transaction. A guarantee and the mechanism enforcing it are different concepts.

retry — What must an application do when serialization checking rejects a transaction?

supported

In PostgreSQL, restart a transaction rejected for serialization failure, including its reads and decisions. Repeating only the write would keep the old decision. Results from an aborted attempt must not be treated as valid.

  • url

target — Why can individually correct concurrent operations go wrong, and how do isolation levels help?

supported

Concurrent transactions can make individually valid decisions from values that become inconsistent when their writes are combined. Atomicity preserves transaction units; isolation constrains their interaction. Serializable requires a result equivalent to a serial order, while weaker levels permit specific anomalies and need application-appropriate reasoning. The individual transaction logic must itself preserve the application’s rules; serializable isolation cannot repair incorrect logic. Its guarantee assumes the relevant transactions participate in serializable execution.
