    array — Why can a known array index be accessed without inspecting preceding entries?

    supported

    An array stores equal-size slots next to each other. If the first slot starts at address b and each slot occupies s units, index i starts at b+i*s. This arithmetic selects the slot directly, without testing earlier entries. The fixed-size word arithmetic and direct memory access are constant-cost primitives in this model; an address identifies a storage location.

    hash — What is a hash code and what must equality imply?

    supported

    A hash function computes an integer code from a key. Equal keys must have equal codes; unequal keys can have equal codes. Computing the code is distinct from converting it to a current table position. The function is a chosen computation, not a scan of the stored table; the example explicitly supplies it as h(k)=k.

    index — How does a code select one of m buckets?

    supported

    For nonnegative hash code h and positive capacity m, h mod m is the remainder after division by m, between 0 and m-1. It selects a numbered bucket. Real implementations can use other index calculations.

    collision — What is a collision and why does the index not identify the key?

    supported

    Different keys can obtain the same bucket index, either from equal hash codes or distinct codes with the same remainder. Sharing a bucket is not key equality.

    chain — How can one bucket retain colliding entries?

    supported

    find — How does lookup find the right value or conclude that it is missing?

    supported

    Compute the query hash, convert it to an index, access that bucket, then compare the query key with stored keys in that bucket. Return the matching entry’s value; reaching the end without equality means missing. This works only while stored entries remain in the bucket computed for an equal query key; otherwise searching one bucket could falsely report missing.

    load — What makes bucket searches longer as a table fills?

    supported

    With n entries and m buckets, the mean bucket length is n/m, called load factor. More entries without more buckets raise this mean; individual buckets can be much longer or shorter.

    expected — Under what assumptions is expected lookup time constant?

    supported

    With bounded n/m and a hash distribution that keeps the selected sequence’s expected length bounded, lookup has O(1) expected bucket work. Expected means an average over a specified randomness model: ODS chooses the hash function’s multiplier randomly for fixed keys. With constant-cost hashing and equality, total expected lookup is O(1): work bounded independently of n, not an exact elapsed time. A fixed identity-hash example demonstrates mechanics, not this probabilistic guarantee.

    worst — Why can one lookup still examine every key?

    supported

    If all n entries select one bucket, a missing-key lookup or a late match scans that bucket, taking O(n) key comparisons. A bounded mean load does not prevent this concentration.

    growth — Why grow the table and what triggers growth?

    supported

    Increasing m controls n/m as n grows. An implementation chooses a load threshold; crossing it can allocate a larger bucket array. In the selected example the threshold is n>m and capacity doubles. Chaining can remain correct without growth but may become slow.

    reindex — Why must entries move when capacity changes?

    supported

    After growth, each entry must be placed at the bucket selected by its hash code under the new capacity. An old bucket index may differ from the new one. Hash codes need not change; redistribution does. Merely appending empty buckets leaves lookup using new indices unable to find some entries. Redistribution can split a collision caused by the old remainder, but keys with equal codes still share an index under any capacity-only remainder change.

    amortized — How can occasional expensive growth have a small long-run insertion cost?

    supported

    At a fixed positive load threshold, doubling allocates a new bucket array and redistributes the stored entries. The capacity and entry count are proportional at those growth points, so rebuilding costs O(n) under constant-cost placement. Capacities 1,2,4,... form a sum less than twice the largest term. Across N insertions from empty, total rebuilding work is O(N), hence O(1) amortized growth overhead per insertion. This averages over a sequence, not over random hashes; one growth insertion can still cost O(n). Bad collision searches can still make total insertion expensive.

    keycost — What costs are hidden by treating key operations as constant?

    supported

    Hashing a string by reading each character costs work proportional to its length L; comparing two strings may also read all L characters. Thus constant expected bucket work need not mean constant total work as key length grows. For such routines a useful bound is hash cost plus the sum of the examined keys’ equality costs plus bucket-access work. The numerical example uses small integers with fixed-cost operations.

    target — Why can dictionary lookup be fast, what do collisions and resizing do, and where does the speed claim stop?

    supported

    Hashing computes where to look, so direct bucket access avoids scanning the whole table when bucket sequences stay short. Equality resolves collisions. Growth maintains room and redistributes entries under the new capacity. Expected constant lookup assumes suitable hashing, controlled load and constant-cost key operations; worst cases can scan all entries and a single growth insertion can be expensive. This graph explains a generic chained dictionary, not CPython internals.

    placement — What condition makes searching only one bucket correct?

    supported

    Every stored entry must be in the bucket computed from its key using the current capacity. Equal query and stored keys must compute the same code, and a stored key’s hash/equality behavior must stay consistent while it is stored. Mutating a key so its code changes can leave its entry in the old bucket.
