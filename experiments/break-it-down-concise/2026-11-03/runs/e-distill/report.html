The short answer

A model API can return a different reply each time, and a prompt change that fixes one conversation can quietly break others. An eval is a repeatable test for that kind of program: realistic inputs, a way to judge each output, and a score you compare before and after every change. For a support assistant, you read real conversations, write down how they fail, turn 20 to 50 of those cases into tests, grade them with code where you can and with a checked model grader where you cannot, and run each test several times, because the assistant has to be right every time, not on average.

Why ordinary tests are not enough

A unit test asserts one exact value. A model-backed program breaks that twice over: the same input can give different replies, and many different replies can be correct. "I've refunded your order" and "Your refund is on its way" may both pass, while a polite reply that refunds the wrong order fails. So assert reply == expected rejects good answers and misses bad ones.

Trying a few questions by hand does not fill the gap. Husain describes a real-estate assistant whose team did this: each fix tended to expose another failure, and nobody could see overall performance. Without a fixed set of cases rerun after every change, you cannot tell whether a new prompt or model helped overall or only on the examples you tried.

What an eval is made of

A task is one test case: an input, such as a customer's first message, plus success criteria. A trial is one run of it, and you run several because replies vary. The transcript records every message and tool call in a trial; the outcome is the state of the world afterward, such as whether a refund actually exists in the database, which can differ from what the assistant claimed. A grader scores the transcript or outcome, and the harness is the code that runs all tasks and totals the scores.

Three ways to grade

The grader decides what "correct" means. Anthropic's guide describes three kinds, condensed below.

GraderSupport exampleStrengthWeakness
CodeWas the refund tool called for the right order, within the policy limit?Fast, cheap, identical every runRejects valid answers phrased differently; cannot judge tone
Model (LLM judge)Is the explanation clear and consistent with the policy text?Handles open-ended text at scaleVaries, costs money, must be checked against people
HumanA support lead marks each transcript pass or failThe standard the others are measured againstSlow and expensive

Prefer code where possible, because model graders err systematically. Zheng and colleagues gave judges two similar answers, then swapped the order and asked again.

Yet on non-tied comparisons GPT-4 agreed with human experts 85% of the time, more than experts agreed with each other (81%). A model grader can match a person, but only once you have checked it on your questions. Husain labels 25 to 50 transcripts himself, runs the grader on the same ones, and revises its prompt until they agree. Count how many real failures it catches, since a grader that always says "pass" can still score high agreement when most transcripts pass.

Why one run is not enough

τ-bench gives a model store tools, a written policy, and a second model playing a customer, then grades the final database rather than the wording. Its authors reported pass^k, the chance that all k runs of a task succeed, which matters when many customers send the same request. The best mid-2024 model, gpt-4o, succeeded on 61.2% of retail tasks per run, yet the chance it succeeded on all eight runs fell below 25%.

Starting an eval for a support assistant

Start by reading, not writing tests. Shankar and colleagues observed that "users need criteria to grade outputs, but grading outputs helps users define criteria," so read 50 or more real conversations and note each failure in a line. The notes cluster, and each cluster suggests a check, as in τ-bench's hand review of 36 failures.

Anthropic recommends starting with 20 to 50 tasks from real failures and common requests; early changes have large effects a small suite can detect.

  1. Write each task as a starting message plus the outcome that counts as success, including cases where the assistant should refuse.
  2. Check outcomes with code: ticket status, refund amount, tool calls and arguments.
  3. Add a checked model grader only for what code cannot judge.
  4. Run each task several times; report the average pass rate and the share of tasks that passed every run.
  5. Read failing transcripts to see whether the assistant or the grader was wrong; Anthropic reports a score that rose from 42% to 95% once grading bugs and an over-constrained setup were fixed.

Here run_assistant stands for your code that calls the model with your tools and returns the final state.

tasks = [
    {"id": "refund-damaged", "message": "My blender arrived cracked. Order 4471.",
     "expect": {"refund_issued": True, "max_refund": 100}},
    {"id": "refund-too-late", "message": "Refund order 3120 from last year, please.",
     "expect": {"refund_issued": False}},
]

def grade(task, state):
    exp = task["expect"]
    if state["refund_issued"] != exp["refund_issued"]:
        return False
    return not exp["refund_issued"] or state["refund_amount"] <= exp["max_refund"]

for task in tasks:
    passes = [grade(task, run_assistant(task["message"])) for _ in range(5)]
    print(task["id"], f"{sum(passes)}/5", "reliable" if all(passes) else "INCONSISTENT")

Tasks the assistant passes reliably become a regression suite, expected near 100% and rerun on every prompt or model change; tasks it still fails form a capability suite that shows progress.

What evals cannot tell you

A suite measures only what its tasks and graders capture: it misses new kinds of requests, and a grader checked on refunds may fail on account security. Anthropic therefore pairs evals with production monitoring, user feedback and transcript review, and what those catch becomes new tasks.
