The short answer

A model API does not return the same answer twice, and a prompt change that fixes one conversation can quietly break others. An eval is a repeatable test for that kind of program: a set of realistic inputs, a way to decide whether each output is acceptable, and a score you can compare before and after every change. For a customer-support assistant, you start by reading real conversations, writing down how they go wrong, turning 20 to 50 of those cases into tests, grading them with code where an answer can be checked and with a carefully checked model grader where it cannot, and running each test several times because a support assistant has to be right every time, not on average.

Why ordinary testing stops working

In ordinary code, add(2, 3) returns 5 every time, so a test can assert the exact value. A program that calls a model API behaves differently in two ways. First, the model samples its words, so the same input can produce different replies on different runs. Second, there is rarely one correct reply: "I've refunded your order" and "Your refund is on its way" may both be fine, while a polite reply that refunds the wrong order is not. An assert reply == expected check fails on good answers and passes nothing useful.

The natural substitute is to try a few questions by hand and see whether the answers look right. Husain calls this a vibe check and describes what happened when one team relied on it. Rechat built an assistant named Lucy for real-estate agents. Early prompt edits helped, then progress stalled: fixing one failure tended to expose another, prompts grew long to cover edge cases, and nobody could see how the assistant performed across all its tasks. The team changed course by putting evaluation at the center of its work. His conclusion is blunt: unsuccessful AI products "almost always share a common root cause: a failure to create robust evaluation systems."

The underlying problem is visibility. Without a fixed set of cases you rerun after every change, you cannot tell whether a new prompt, a new model version, or a new tool made the assistant better overall or just better on the three examples you happened to try.

What an eval is made of

Anthropic's guide gives the parts names that are worth learning, because most tools and articles use them. A task is one test case: an input, such as a customer's opening message, plus success criteria. A trial is one run of that task; because replies vary, you run several. The transcript (also called a trace) is the full record of a trial: every message, tool call and intermediate result. The outcome is the state of the world when the trial ends, such as whether a refund row now exists in the database, which can differ from what the assistant claimed. A grader is the logic that scores the transcript or the outcome. A collection of tasks is a suite, and the code that runs the suite and totals the scores is the harness.

If you can write a small Python program, you can build a harness: a list of task dictionaries, a loop that calls your assistant on each one several times, a few grading functions, and a printed pass rate. Specialised platforms exist, but Husain's advice is to start with tools you already have and build something specific to your problem.

Three ways to grade, and their trade-offs

The hardest design choice is the grader, because it decides what "correct" means. Anthropic's guide sorts graders into three kinds, and the table below condenses its comparison.

GraderExamples for a support assistantStrengthWeakness
CodeWas the refund tool called with the right order ID? Is the refund at most the policy limit? Did the reply avoid leaking an internal ID?Fast, cheap, identical every run, easy to debugRejects valid answers phrased differently; cannot judge tone or helpfulness
Model (an LLM judge)Does the reply explain the resolution clearly and match the policy text the tool returned?Handles open-ended text; scales to many casesVaries between runs, costs money, and must be checked against people
HumanA support lead marks each transcript pass or fail and writes whyThe standard the others are measured againstSlow and expensive

Use code wherever an answer can be checked mechanically, and reserve the model grader for what code cannot see. The model grader is attractive because it reads like a person, which is also why it needs scrutiny: it can be wrong in systematic ways. Zheng and colleagues measured this. They gave judge models two similar answers, then swapped the order and asked again.

The same paper found judges preferred answers padded with a rephrased copy of their own list: two of the three judges fell for it on 91.3% of 23 answers, GPT-4 on 8.7%. Yet the news is not all bad. On non-tied comparisons, GPT-4's verdicts agreed with human experts 85% of the time, while two human experts agreed with each other 81% of the time. A model grader can be about as consistent as a person, but only once you have checked that it is, on your kind of question.

Checking means comparing it with your own labels. Husain's process is to label 25 to 50 transcripts yourself as pass or fail with a short critique, run the model grader on the same transcripts, put both in a spreadsheet, and rewrite the grader's prompt until it agrees with you. He warns that a plain agreement percentage misleads when most transcripts pass, because a grader that always says "pass" scores well. Count separately how many real failures it catches and how many of its failure flags are real.

Why one run is not enough

Because replies vary, a single trial tells you little about whether the assistant handles a request reliably. τ-bench measured this directly in a simulated retail store. Each task gives the model tools such as order lookup and exchange, a written store policy, and a second model playing a customer with a specific goal. The grader ignores the wording of the conversation and compares the store's database at the end with the state it should be in.

The authors ran each task many times and reported two numbers. pass@k is the chance that at least one of k runs succeeds. pass^k is the chance that all k runs succeed, which is the number that matters when many customers send the same request. The best model in mid-2024, gpt-4o, succeeded on 61.2% of retail tasks per run, but the chance it succeeded on all eight runs of a task fell below 25%.

Starting an eval for a customer-support assistant

The first step is reading, not writing tests. You cannot list everything "good" means before you see your assistant's answers; Shankar and colleagues observed that "users need criteria to grade outputs, but grading outputs helps users define criteria." So gather 50 or more real or realistic conversations, read every one, and write a one-line note on each failure. Husain's rule of thumb is to keep reading until you stop learning anything new.

Your notes will cluster into a few kinds of failure, and each kind points to a grader. τ-bench's authors did this by hand for 36 failed gpt-4o conversations.

From those notes, build the suite. Anthropic's guide recommends starting with 20 to 50 simple tasks drawn from real failures and common requests, because early changes have large effects that a small suite can detect. The steps below put the pieces together.

  1. Write each task as a starting message, any customer details the assistant should look up, and the outcome that counts as success. Include cases where the assistant should act and cases where it should refuse, so you do not reward an assistant that refunds everything.
  2. Check the outcome with code first: the ticket status, the refund amount, which tools were called and with what arguments. Anthropic's example refund task checks that identity was verified, the refund tool was called with an amount within the limit, and a confirmation was sent.
  3. Add a model grader only for what code cannot judge, such as whether the explanation is clear and matches the policy, and check it against 25 to 50 of your own labels before trusting it.
  4. Run each task several times and report both the average pass rate and the share of tasks that passed on every run.
  5. Read the failing transcripts after each run to decide whether the assistant or the grader was wrong. Anthropic reports one benchmark where its model scored 42% until bugs in the grading and an over-constrained setup were fixed, then 95%.

A minimal harness in Python looks like this. run_assistant stands for your own code that calls the model API with your tools and returns the transcript and the final state.

tasks = [
    {"id": "refund-damaged",
     "message": "My blender arrived cracked. Order 4471.",
     "expect": {"refund_issued": True, "max_refund": 100}},
    {"id": "refund-too-late",
     "message": "I want a refund for order 3120 from last year.",
     "expect": {"refund_issued": False}},
]

def grade(task, result):
    state, exp = result["state"], task["expect"]
    if state["refund_issued"] != exp["refund_issued"]:
        return False
    if exp["refund_issued"] and state["refund_amount"] > exp["max_refund"]:
        return False
    return True

TRIALS = 5
for task in tasks:
    passes = [grade(task, run_assistant(task["message"])) for _ in range(TRIALS)]
    print(task["id"], f"{sum(passes)}/{TRIALS}",
          "reliable" if all(passes) else "INCONSISTENT")

Once the assistant reliably passes a task, it moves into a regression suite, a set you expect to stay near 100% and run on every prompt or model change, the way you run unit tests before merging code. New, still-failing tasks form a capability suite that starts with a low pass rate and shows whether changes move you forward. Husain runs cheap code checks on every change, model and human review on a regular schedule, and A/B tests with real users only for significant product changes on a mature product.

What evals can and cannot tell you

An eval only measures what its tasks and graders capture. A suite built from last month's conversations will miss new kinds of requests, a simulated customer behaves more predictably than a real one, and a model grader that agreed with you on refunds may not agree on account security. That is why the sources treat evals as one layer among several: production monitoring, user feedback and periodic human review catch what the suite misses, and what they catch becomes new tasks. The practical consequence is that an eval suite is never finished. It grows from the failures you read, and its value comes from rerunning the same cases every time you change the assistant.
