Transaction isolation.

Sources

A Critique of ANSI SQL Isolation Levels↗

Hal Berenson, Phil Bernstein, and colleagues · Conference paper and Microsoft Research technical report, ACM SIGMOD · June 1995

This paper pinned down what the SQL standard's isolation levels actually guarantee. Its authors include Jim Gray, who won the Turing Award for transaction-processing research, and Jim Melton, editor of the SQL standard. They write out exact sequences of reads and writes and show which ones each level lets through, and they prove that the standard's plain-English rules leave holes: lost updates, dirty writes, and write skew slip past them. Because the arguments are logical proofs rather than measurements, they still hold. Its descriptions of 1995 products do not describe today's versions, and later researchers reworked its definitions so they do not assume locking.

PostgreSQL 18 Documentation: Transaction Isolation↗

The PostgreSQL Global Development Group · Official product documentation, postgresql.org · Current manual, accessed November 2026

PostgreSQL's developers wrote this page to say exactly what each level does in the current release. It gives the standard's four levels in a table, short SQL examples of what goes wrong at each, and the error a transaction receives when the database refuses a conflicting interleaving. It confirms that Read Committed is PostgreSQL's default, that its Repeatable Read is snapshot isolation, and that its Serializable mode works by aborting a transaction the application must retry. It describes PostgreSQL only.

MySQL 8.4 Reference Manual: Transaction Isolation Levels↗

Oracle Corporation · Official product documentation, dev.mysql.com · MySQL 8.4 manual, accessed November 2026

The vendor's manual for MySQL's main storage engine, InnoDB, in the current long-term-support release. It confirms that the default level is Repeatable Read and explains that plain SELECTs read from a snapshot while UPDATEs act on the newest committed data; the manual itself warns these views can be "inconsistent with each other." The vendor calls its default strongly consistent, but independent tests found it lets lost updates through, so it should be read alongside those tests.

Serializable Snapshot Isolation in PostgreSQL↗

Dan R. K. Ports and Kevin Grittner · Conference paper, Proceedings of the VLDB Endowment (VLDB 2012) · August 2012

The two engineers who built PostgreSQL's Serializable mode explain why snapshot isolation is not enough, using a two-doctor on-call example, and measure what full protection costs. In their benchmarks serializable mode ran within about 7% of snapshot isolation, while classic locking was far slower on read-heavy work. Those numbers come from 2012 hardware, PostgreSQL 9.1, and a locking implementation the authors built for comparison, so they are one measured case, not a general rule. A bug in this mechanism was found in 2020 and fixed.

Highly Available Transactions: Virtues and Limitations↗

Peter Bailis, Aaron Davidson, and colleagues · Conference paper (extended version), VLDB 2014 / arXiv · February 2013

Only one table from this paper is used: database researchers' survey of default and strongest isolation levels in 18 databases as of January 2013, compiled from vendor documentation. Only 3 of the 18 defaulted to serializable. It is a historical snapshot of old versions, some of products that no longer exist, so it shows that weak defaults are normal, not what any product does today.

ACIDRain: Concurrency-Related Attacks on Database-Backed Web Applications↗

Todd Warszawski and Peter Bailis · Conference paper, ACM SIGMOD · May 2017

Stanford researchers tested whether real shopping software breaks when an attacker sends many requests at once, and confirmed 22 such vulnerabilities in 12 popular e-commerce platforms by actually triggering them. Five came from the database's default weak isolation; the other 17 came from code that never grouped its steps into one transaction, which no isolation level can fix. Its "2 million websites" figure counts sites running the affected software, not sites attacked, and some attacks needed an added network delay to trigger reliably.

Hermitage: Testing Transaction Isolation Levels↗

Martin Kleppmann and contributors · Open test suite and results, GitHub · First published November 2014, updated January 2026

A set of step-by-step scripts for two database sessions, each trying to trigger one named anomaly, written by the author of Designing Data-Intensive Applications. Anyone can rerun them, so the results can be checked rather than trusted. Its results table shows that level names do not line up across products. The tests were run by hand on particular versions, some old (PostgreSQL 9.3.5), and can show that an anomaly occurs but cannot prove it never will. The PostgreSQL results agree with the current manual.

PostgreSQL 12.4 Release Notes↗, with Jepsen: PostgreSQL 12.3↗

The PostgreSQL Global Development Group · Release notes · August 2020; Kyle Kingsbury · Independent consistency analysis, jepsen.io · June 2020

Jepsen, an independent tester that runs automated workloads against databases and checks the results against formal definitions, found in 2020 that PostgreSQL's Serializable mode could let a rare three-transaction anomaly through. The project fixed it that August. The bug no longer describes current behavior; it shows that a guarantee is only as good as its implementation. The Jepsen report was read only in summary, so the release notes are quoted instead.

The short answer

Each operation is correct when it runs alone, but a database runs many at once and interleaves their steps. If one operation reads a value, and another changes that value before the first finishes acting on what it read, the first one acts on stale information. The combined result can then match no order in which the operations could have run one at a time, and that is the definition of wrong. Isolation levels are rules about which of these interleavings the database will allow. Weaker levels allow more of them in return for less waiting; the strongest level, Serializable, allows only interleavings equivalent to some one-at-a-time order, and it enforces this by making transactions wait or by cancelling one so the application can retry it. Most databases do not use that level by default, and the same level name means different things in different products.

What "correct" means for one transaction

A transaction is a group of SQL statements, started with BEGIN and ended with COMMIT, that the database treats as one unit. Berenson and colleagues define it as a group of actions that moves the database "from one consistent state to another." Consistent means the data still obeys its rules, which database people call invariants: an account balance never goes below zero, a transfer leaves the total amount of money unchanged, at least one doctor is on call. A transaction is individually correct when, run with nothing else happening, it keeps every invariant true.

Most application logic follows one pattern. It reads a value with a SELECT, makes a decision or a calculation in application code, and writes the result with an UPDATE. This read-modify-write pattern is safe when nothing else touches the data between the read and the write. The rest of this explanation is about what happens when something does.

What "correct" means for transactions running together

Run transactions one after another with no overlap, and every result is correct, because each one starts from a consistent state and leaves one behind. Running them one at a time is called a serial order. The reference definition of correct concurrent execution follows from that. In Berenson and colleagues' words, an execution "is serializable if it is equivalent to a serial history": the end result must be one that some one-at-a-time order could have produced. Ports and Grittner state the payoff: if each transaction is shown to do the right thing when run alone, it also does so in any serializable mix. Nobody has to reason about how pairs of transactions interact.

The trouble is that databases do not run transactions one at a time. They serve many connections at once and interleave their statements so that no connection waits for all the others. Nothing is wrong with any single statement. The problem is the order in which steps from different transactions land.

How two correct operations produce a wrong result

Suppose an account holds 100. Transaction A adds 20 and transaction B adds 30, each by reading the balance and writing back the new total. Run A then B and the balance ends at 150; run B then A and it also ends at 150. Now let the steps interleave as below.

StepTransaction A (+20)Transaction B (+30)Stored balance
1SELECT balance → 100100
2SELECT balance → 100100
3UPDATE balance = 120; COMMIT120
4UPDATE balance = 130; COMMIT130

Both committed, yet the balance is 130. A's 20 vanished, because B computed its total from a value A had already replaced. This is a lost update, and Berenson and colleagues write it as the history r1[x=100] r2[x=100] w2[x=120] c2 w1[x=130] c1, where r means read, w write, c commit, and the digit names the transaction. Their conclusion: "The final value of x contains only the increment of 30 added by T1."

The general mechanism is a conflict. Two transactions touch the same item and at least one of them writes it, so one of them decides or writes based on a value the other changes before it finishes. In the table, B's read at step 2 and A's write at step 3 conflict: B must come before A, because B read the old value, and A must come before B, because B overwrote A's write. No serial order satisfies both requirements, so the result is wrong.

The same pattern costs real money when the check guards a withdrawal. Warszawski and Bailis open their paper with four lines of code that are correct alone.

Two simultaneous calls of version (a) can both read $100, both pass the check that $100 covers $99, and each allow $99 out, so $198 leaves an account that held $100. Version (b) looks like the fix, but the caption warns it is still vulnerable at Read Committed or below unless the code takes an explicit lock with SELECT ... FOR UPDATE. Wrapping steps in a transaction groups them; it does not by itself stop another transaction from reading the same balance in between.

    Try "Play the bad order" at each level. At Read Committed the balance ends at 130 with no error. At Repeatable Read the same order makes B's write fail, and pressing retry lets B start over, read 120, and finish at 150. The stronger level did not compute the right answer by itself; it refused the wrong one and handed the work back to the application. Also try running all of A before B: both levels give 150. The bug needs an unlucky overlap, which is one reason Ports and Grittner describe these anomalies as typically appearing as "silent data corruption" rather than as errors.

    One detail matters for practice. If the code writes the increment as a single statement, UPDATE accounts SET balance = balance + 20 WHERE ..., PostgreSQL's Read Committed does not lose the update: the second UPDATE waits for the first to commit and then applies its addition to the newly committed row, as the PostgreSQL manual describes. The lost update needs the value to pass through application code between a SELECT and an UPDATE.

    The failure patterns have names

    Database researchers have catalogued the interleavings that go wrong, and the names appear throughout database documentation. Each one describes a way a transaction can act on information that another transaction is changing.

    NameWhat happens
    Dirty writeA transaction overwrites another's write before that write commits.
    Dirty readA transaction reads another's uncommitted write, which might still be rolled back and never officially exist.
    Lost updateTwo read-modify-writes on the same row; the second overwrites the first, as in the deposit example.
    Non-repeatable (fuzzy) readReading the same row twice in one transaction gives different values because another transaction committed in between.
    Read skewReading two related rows at different moments and seeing a mix of before and after, such as half of a transfer.
    PhantomRepeating a search (a WHERE query) returns a different set of rows because another transaction inserted or deleted matching rows.
    Write skewTwo transactions read overlapping data, each checks a rule, and each writes a different row; together they break the rule.

    Read skew needs no write conflict at all. Berenson and colleagues give the case of $40 moving from account x (50) to account y (50). A report that reads x after the withdrawal and y before the deposit sees 10 + 50, a total of 60 instead of 100, even though it only read.

    How isolation levels help

    Preventing every bad interleaving costs something, because the database must make some transactions wait or cancel them. Berenson and colleagues' first sentence states the bargain: running transactions "at different isolation levels allows application designers to trade throughput for correctness." An isolation level is a setting, chosen per transaction with SET TRANSACTION ISOLATION LEVEL ..., that says which anomalies the application is willing to risk.

    The SQL standard names four levels and defines the lower three by which of three phenomena each must prevent: dirty reads, non-repeatable reads, and phantoms.

    Each step down the table forbids one more phenomenon. Notice the bottom row's label, "ANOMALY SERIALIZABLE." The paper's central finding is that forbidding these three phenomena is not the same as serializability, which the authors call a common misconception. Lost updates, dirty writes, and write skew are not among the three, so a database can satisfy the standard's wording and still let them through. The authors added those anomalies and placed each level against all of them.

    Read down the Lost Update column: Read Committed allows it, and both Repeatable Read and Snapshot prevent it. Then read across the Snapshot and Repeatable Read rows. Each leaves a different gap, phantoms in one and write skew in the other, so neither is simply stronger. Only the Serializable row says "Not Possible" everywhere. "Repeatable Read" here means the paper's locking definition, and the next sections show that products do not all match it.

    Two ways databases enforce the levels

    Locks

    Before reading or writing a row, a transaction takes a lock on it, and a conflicting request waits. In a locking database the levels differ mainly in how long read locks last: none at Read Uncommitted, released right after each read at Read Committed, held to commit at Repeatable Read, and held to commit on search conditions too at Serializable (Berenson and colleagues, Table 2). Write locks are held to commit throughout. Holding every lock until commit, called two-phase locking, gives serializability.

    Snapshots

    The database keeps old versions of rows, and each statement or transaction reads a consistent snapshot as of some moment, so in PostgreSQL's words "reading never blocks writing and writing never blocks reading." Writers still lock the rows they change, and under snapshot isolation the first to commit a change wins while the other is cancelled. PostgreSQL, Oracle, and plain SELECTs in MySQL's InnoDB work this way.

    What PostgreSQL promises

    PostgreSQL's manual uses the same shape as the standard's table but adds a fourth column for any result that matches no one-at-a-time order.

    "Serialization Anomaly" is possible everywhere except Serializable, which is the plain-language version of Berenson's point. "Allowed, but not in PG" marks places where PostgreSQL does more than the standard requires: it treats Read Uncommitted as Read Committed, and its Repeatable Read prevents phantoms. The manual says "Read Committed is the default isolation level in PostgreSQL" and that its Repeatable Read "is implemented using a technique known in academic database literature ... as Snapshot Isolation."

    The gap that snapshots leave

    Snapshot isolation stops dirty reads, values shifting mid-transaction, and lost updates. It still allows write skew, which is why it is not serializable. Ports and Grittner's example is two doctors, Alice and Bob, with the rule that at least one must stay on call.

    Each transaction counts two doctors on call, so each decides it is safe to leave. Run one after the other, the second would count one doctor and stop. Under snapshot isolation both count from the same snapshot, and they update different rows, Alice's and Bob's. As the authors put it, the write locks "don't solve this problem, because the two transactions modify different rows and thus do not conflict." Both commit, and nobody is on call. No row was overwritten, so the lost-update protection never triggers.

    PostgreSQL's manual gives a second version in SQL. A table holds rows with classes 1 and 2. Transaction A sums class 1 (30) and inserts that sum as a class 2 row, while B sums class 2 (300) and inserts it as a class 1 row. At Repeatable Read both commit. At Serializable one is rolled back with "could not serialize access due to read/write dependencies among transactions," because, as the manual explains, if A had run first B would have computed 330, not 300, and the other order would change A's sum.

    Serializable mode in PostgreSQL works by watching for this pattern of read and write dependencies and cancelling a transaction that would complete it. A locking database prevents write skew a different way: Serializable holds read locks on the rows and search conditions each transaction read, so the second writer waits. At weaker levels an application can close this particular gap itself by locking the rows it counts with SELECT ... FOR UPDATE.

    "Repeatable read" stops lost updates in PostgreSQL but not in MySQL, where the ACIDRain authors also reported being "surprised to trigger Lost Updates under MySQL Repeatable Read." By Hermitage's tests, Oracle's "serializable" is snapshot isolation and still allows write skew. The MySQL manual itself hints at the cause: plain SELECTs read a snapshot while UPDATEs act on the newest committed data, and it warns these can be inconsistent with each other.

    Defaults are weak

    Databases usually start each transaction at a weaker level than Serializable unless the application asks. The current manuals say PostgreSQL defaults to Read Committed and MySQL's InnoDB to Repeatable Read. A 2013 survey of 18 databases shows how common this was.

    Only 3 of the 18 defaulted to serializability, and 8 did not offer it at all; Oracle's maximum was snapshot isolation. The versions are old and some products are gone, so the table shows the norm in 2013, which current PostgreSQL and MySQL manuals still match, not any product's current setting.

    What protection costs

    Stronger levels prevent anomalies by blocking a transaction until a conflicting one finishes, or by aborting it with a serialization failure. PostgreSQL's manual is direct about the consequence: "Applications using this level must be prepared to retry transactions due to serialization failures." Retrying means rolling back and running the whole transaction again, reading fresh values, as in the model above.

    How much throughput this costs depends on the implementation and the workload. Ports and Grittner measured their PostgreSQL Serializable mode against snapshot isolation and against strict two-phase locking, the classic lock-based way to get serializability.

    The vertical axis is throughput as a fraction of snapshot isolation's. The SSI line, PostgreSQL's serializable mode, stays near the top, while the S2PL line, locking-based serializable, drops to under half when most transactions only read, because readers must hold locks that make writers wait. The authors summarize the cost of their serializable mode as "less than 7% relative to snapshot isolation." On an auction-site benchmark the pattern held.

    Serializable mode kept about 97% of snapshot isolation's throughput (422 against 435 requests per second), while locking got under half (208) and aborted more often. These are measurements of PostgreSQL 9.1 on 2012 hardware, against a locking implementation the authors built themselves, so they show that full protection can be cheap, not that it always is.

    What isolation cannot fix

    Isolation protects only what is inside one transaction. ACIDRain's authors found 22 concurrency vulnerabilities in 12 e-commerce platforms, including repeated gift-card spending and free items. Five came from weak default isolation, four of them lost updates.

    Raising each database to its strongest level stops all or all but one of the five. The "Remaining" column is the larger point: 17 vulnerabilities survive any level, because the code never put the read and the write in the same transaction. The paper also quotes the Bitcoin exchange Flexcoin, which closed in 2014 after an attacker sent "thousands of simultaneous requests" to move coins between accounts before balances were updated.

    At weaker levels, applications can close specific gaps directly. A single-statement update such as balance = balance + 20 avoids the read-modify-write gap; SELECT ... FOR UPDATE locks the rows a decision depends on; and a constraint the database enforces, such as a check that a balance stays non-negative, refuses a bad result no matter how it arose. Each of these fixes one known pattern, which is why Ports and Grittner argue for Serializable when a system has too many transactions to check every pair, as in the Wisconsin court system where Grittner worked.

    Finally, a guarantee is only as good as the code behind it. In 2020 independent testing found that PostgreSQL's serializable mode could, in a rare three-transaction case, let an anomaly through; the 12.4 release notes record that this "could allow a serializable transaction to commit when it should have failed with a serialization error," and the bug was fixed. Tests like Hermitage's can show that an anomaly happens, but cannot prove it never will. The practical rule is to put each read-decide-write sequence in one transaction, know which level your database actually runs and what that level means in that product, and use Serializable with retries, or explicit locks, where an invariant spans rows.
