Database transaction isolation.

Sources

A Critique of ANSI SQL Isolation Levels↗

Hal Berenson, Phil Bernstein, and colleagues · Conference paper and Microsoft Research technical report, ACM SIGMOD · June 1995

The authors include Jim Gray, who received the Turing Award for transaction processing, and Jim Melton, editor of the SQL standard. They write out exact sequences of reads and writes and prove which ones each isolation level lets through, showing that the standard's definitions miss lost updates and write skew. Proofs about definitions do not age, but its descriptions of 1995 products do not describe today's versions.

The vendor's manual confirms MySQL's default level and explains how its plain reads and its updates see different data. It calls the default strongly consistent, a description the independent tests below do not support.

Serializable Snapshot Isolation in PostgreSQL↗

Dan R. K. Ports and Kevin Grittner · Conference paper, Proceedings of the VLDB Endowment (VLDB 2012) · August 2012

The two engineers who built PostgreSQL's Serializable mode explain why snapshot isolation falls short, how their mode catches the gap, and what it costs in benchmarks. The measurements come from 2012 hardware, PostgreSQL 9.1, and a locking implementation the authors built themselves for comparison, so they are one measured example rather than a general rule.

Todd Warszawski and Peter Bailis · Conference paper, ACM SIGMOD · May 2017

Stanford researchers found 22 concurrency bugs in 12 popular e-commerce platforms and confirmed each by triggering it. Its reach figure of about 2 million websites counts sites running the affected software, not sites attacked, and some attacks needed an added network delay to trigger reliably.

Jepsen, an independent tester that checks databases against formal definitions, found a rare case in which PostgreSQL's Serializable mode let an anomaly through, and the project's release notes record the fix. The Jepsen report was read only in summary, so the release notes supply the exact wording.

The short answer

Each transaction is checked as if it runs alone. A database runs many at once by interleaving their steps, and when two of them touch the same data and at least one writes it, one can act on a value the other is about to change. The result can then match neither "A, then B" nor "B, then A," and that mismatch is what wrong means here. Isolation levels are settings that tell the database how many of those interleavings to forbid. Weak levels forbid few and rarely make anyone wait. Serializable forbids every interleaving whose result no one-at-a-time order could produce, and it pays by making transactions wait or by aborting one so the application can run it again. Most databases default to a weaker level, and the same level name promises different things in different products.

What "correct" means for one transaction and for many

A transaction is a group of SQL statements between BEGIN and COMMIT that the database treats as one unit. Applications depend on rules the data must always satisfy, such as "a balance never drops below zero" or "at least one doctor is on call." These rules are called invariants. A transaction is individually correct when, started on data that satisfies the rules and run with nothing else happening, it leaves data that still satisfies them.

That gives a test for many transactions at once. Run them one at a time, in any order, and each starts from correct data and leaves correct data, so every one-at-a-time order (a serial order) ends correct. An interleaved run is called serializable when its result equals that of some serial order. Ports and Grittner draw the consequence: if each transaction does the right thing alone, it does the right thing in any serializable mix. Asking whether a concurrent run is correct therefore becomes asking whether some serial order could have produced it.

How two correct transactions produce a wrong result

Suppose an account holds 100. Transaction A deposits 20 and transaction B deposits 30. Each reads the balance with a SELECT, adds its amount in application code, and writes the total back with an UPDATE. Run in either order, they leave 150. The database, though, runs statements from different connections as they arrive, so this sequence is allowed at the default level of PostgreSQL and MySQL:

Neither transaction has a bug. B computed 130 from a value that A had already replaced, so A's committed deposit vanished. In any serial order one of the two would have read the other's result. Here each read the balance from before the other's write, so each behaved as if it ran first, and both cannot be first. That is why 130 matches no serial order.

Two conditions produce every failure of this kind. The transactions must conflict, meaning they touch the same data and at least one writes it. And one of them must base a decision or a write on a value that the other changes, or has not yet committed, before the first finishes. Steps that do not conflict can be reordered freely without changing the result, which is why databases can interleave most work safely.

The read-then-write shape matters. In PostgreSQL at Read Committed, a single statement UPDATE accounts SET balance = balance + 20 WHERE id = 1 does not lose the update: the second such statement waits for the first to commit and then applies to the new value. The bug needs the value to pass through application code between a SELECT and an UPDATE.

The failure patterns have names

Database literature names each recurring interleaving, and isolation levels are defined by which of them they forbid:

  • A dirty read reads another transaction's change before it commits, so the change may later be rolled back and never officially exist.
  • A non-repeatable read gets different values from reading the same row twice in one transaction, because another transaction committed a change in between.
  • A phantom appears when a repeated search such as WHERE on_call = true returns a different set of rows because another transaction inserted or deleted one.
  • A lost update is the deposit example above.
  • Read skew reads two related rows at different moments. If 40 moves from account x (50) to account y (50), a report that reads x after the move and y before it sees 10 + 50 = 60 instead of 100.
  • Write skew happens when two transactions read the same data, each checks a rule, and each then writes a different row, so that together they break the rule. An example follows below.
  • A dirty write overwrites another transaction's uncommitted change. Every real isolation level prevents it.

Isolation levels forbid more interleavings at each step

The SQL standard names four levels and defines the lower three by which of three phenomena, dirty read, non-repeatable read, and phantom, each must rule out. PostgreSQL's manual presents the standard's table with one column added.

Databases enforce these levels in two main ways, and both explain why stronger costs more. A locking database makes a transaction lock a row before reading or writing it, and a conflicting request waits. Write locks are held until commit at every level. The levels differ in read locks: none at Read Uncommitted, released right after each read at Read Committed, held until commit at Repeatable Read, and at Serializable also held on search conditions, so no new matching row can appear. Holding every lock until commit guarantees serializability, but transactions wait for each other.

Multiversion databases, including PostgreSQL, MySQL's InnoDB engine for plain reads, and Oracle, keep old versions of rows and let readers see a consistent snapshot, so in PostgreSQL's words "reading never blocks writing and writing never blocks reading." At Read Committed each statement gets a fresh snapshot. Under snapshot isolation the whole transaction reads one snapshot from its start, and when two transactions write the same row, the later one is refused. In the deposit example at PostgreSQL's Repeatable Read, B's UPDATE fails with "could not serialize access due to concurrent update." The application rolls B back and runs it again; the rerun reads 120 and writes 150.

The standard's ladder has gaps

Berenson and colleagues showed that forbidding the standard's three phenomena does not guarantee serializability, and that lost updates and write skew fall outside them entirely. Their fuller table lists each level against eight anomalies.

Write skew is the gap that survives snapshot isolation, and Ports and Grittner's example shows why. The rule is that at least one doctor stays on call.

Serializable closes this gap. A locking engine makes one transaction wait on the other's read locks. PostgreSQL instead tracks what each transaction read and, when it finds a pattern of dependencies no serial order could produce, aborts one transaction with "could not serialize access due to read/write dependencies among transactions." Either way the guarantee arrives as waiting or as an error, not as a silent fix, and PostgreSQL's manual is explicit that "Applications using this level must be prepared to retry transactions due to serialization failures."

Names and defaults differ between products

A level's name says less than its tested behavior. PostgreSQL's manual states that its Repeatable Read "is implemented using a technique known … as Snapshot Isolation," so it refuses lost updates but allows write skew. MySQL's InnoDB uses Repeatable Read by default, yet its plain SELECTs read a snapshot taken at the first read while its UPDATEs act on the newest committed data. Hermitage's tests and the ACIDRain authors both triggered lost updates under it. In Hermitage's tests, Oracle's level named "serializable" behaves as snapshot isolation and allows write skew.

Defaults are usually weaker than Serializable. PostgreSQL defaults to Read Committed and MySQL to Repeatable Read, so the deposit example runs unprotected in both unless the application asks for more. In a January 2013 survey of vendor documentation by Bailis and colleagues, only 3 of 18 databases defaulted to serializability, and 8 did not offer it at all.

The cost depends on how serializability is built

Across their benchmarks, the authors report a cost of less than 7% relative to snapshot isolation. On an auction-site benchmark, SSI served 422 requests per second against snapshot isolation's 435, while lock-based serializability served 208. How serializability is built matters more than the level's name, though these are one database's numbers on one set of workloads.

What isolation cannot fix

Isolation protects only statements inside the same transaction. Of ACIDRain's 22 confirmed vulnerabilities, which let attackers reuse gift cards, get free items, and corrupt inventory, 5 came from the databases' default weak isolation (4 lost updates and 1 phantom). The other 17 came from code that never put the related steps in one transaction, which no isolation level can repair. The Bitcoin exchange Flexcoin closed in 2014 after, in its own statement, an attacker sent "thousands of simultaneous requests" to move coins out before balances updated.

At weaker levels, applications close specific gaps by hand. They write the change as one statement (SET balance = balance + 20), lock the rows they read before deciding with SELECT … FOR UPDATE, let the database enforce the rule with a constraint, or create a row that both transactions must write so their conflict becomes visible to the database. Each fix covers only the case it was written for, which is why Ports and Grittner's court-system users, with hundreds of tables and more than 20 programmers, chose Serializable rather than checking every pair of transactions.

Guarantees also depend on the implementation. In 2020 Jepsen found that PostgreSQL's Serializable mode, in a rare case with three transactions, could let an anomaly through; the 12.4 release notes record that the bug "could allow a serializable transaction to commit when it should have failed with a serialization error," and it is fixed. When correctness depends on reading a value and then writing based on it, the safe choices are to run at Serializable and retry on failure, or to know exactly which anomaly your product's level allows and close that one explicitly.
