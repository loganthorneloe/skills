Transaction isolation, from first principles.

Sources and how far to trust them

A Critique of ANSI SQL Isolation Levels↗

Hal Berenson, Phil Bernstein, and colleagues · Conference paper and Microsoft Research technical report, ACM SIGMOD · June 1995

This paper pinned down what the SQL standard's isolation levels actually guarantee. Its authors include Jim Gray, who won the Turing Award for transaction processing, and Jim Melton, editor of the SQL standard. They write out exact sequences of reads and writes and show which ones each level lets through, proving that the standard's English rules leave holes: lost updates, dirty writes, and write skew slip past them. It also gave the first precise definition of snapshot isolation. Its arguments are logical proofs rather than measurements, so they still hold, but its descriptions of 1995 products don't describe today's versions. Later researchers reworked its definitions so they don't assume locking, and testing tools use that newer vocabulary.

PostgreSQL 18 Documentation: Transaction Isolation↗

The PostgreSQL Global Development Group · Official product documentation, postgresql.org · Current manual, accessed November 2026

The PostgreSQL developers wrote this page to say exactly what each level does in the current release. It gives the standard's four levels in a table, short SQL examples of what goes wrong at each, and the error a transaction gets when the database refuses a conflicting interleaving. It confirms that Read Committed is PostgreSQL's default, that its Repeatable Read is snapshot isolation, and that its Serializable mode aborts a transaction the application must retry. It describes only PostgreSQL.

MySQL 8.4 Reference Manual: Transaction Isolation Levels↗

Oracle Corporation · Official product documentation, dev.mysql.com · MySQL 8.4 manual, accessed November 2026

MySQL's own manual for its main storage engine, InnoDB, in the current long-term-support release. It confirms that the default level is Repeatable Read and explains that plain SELECTs read from a snapshot while UPDATEs and locking reads act on the newest committed data. The vendor calls the default strongly consistent, but independent tests (Hermitage and ACIDRain, below) found it lets lost updates through, so read it alongside them.

Serializable Snapshot Isolation in PostgreSQL↗

Dan R. K. Ports and Kevin Grittner · Conference paper, Proceedings of the VLDB Endowment (VLDB 2012) · August 2012

The two engineers who built PostgreSQL's Serializable mode explain how it works and measure what it costs. Its two-doctors example shows why snapshot isolation is not enough. In their benchmarks serializable mode ran within about 7% of snapshot isolation, while classic locking was far slower on read-heavy work. Those numbers come from 2012 hardware, PostgreSQL 9.1, and a locking implementation the authors built themselves, so they are one measured example, not a general cost.

Highly Available Transactions: Virtues and Limitations↗

Peter Bailis, Aaron Davidson, and colleagues · Conference paper (extended version), VLDB 2014 / arXiv · February 2013

This report uses one table from it: a survey of default and strongest isolation levels in 18 databases as of January 2013, compiled from vendor documentation. Only 3 defaulted to serializable. It is a historical snapshot of old versions, some of products that no longer exist, so it supports the general point that weak defaults are normal but says nothing about any database's current default.

ACIDRain: Concurrency-Related Attacks on Database-Backed Web Applications↗

Todd Warszawski and Peter Bailis · Conference paper, ACM SIGMOD · May 2017

Stanford researchers tested whether real shopping software breaks when an attacker sends many requests at once, and confirmed 22 such vulnerabilities in 12 popular e-commerce platforms by triggering each one. Five came from the database's default weak isolation; the other 17 came from code that never grouped its steps into one transaction, which no isolation level can fix. Its "2 million websites" figure counts sites running the affected software, not sites attacked, and some attacks needed an added network delay to trigger reliably.

Hermitage: Testing Transaction Isolation Levels↗

Martin Kleppmann and contributors · Open test suite and results, GitHub · First published November 2014, updated January 2026

A suite of step-by-step scripts for two database sessions, each trying to trigger one specific anomaly. Anyone can rerun them, so the results can be checked rather than taken on trust. Its summary table compares what each product's level is called with what it actually prevents. The tests were run by hand on particular versions, some old (the PostgreSQL scripts used 9.3.5), and they can show that an anomaly occurs but cannot prove it never will. The PostgreSQL results agree with the current manual.

PostgreSQL 12.4 Release Notes↗, with Jepsen: PostgreSQL 12.3↗

The PostgreSQL Global Development Group · Release notes · August 2020; Kyle Kingsbury · Independent consistency analysis, jepsen.io · June 2020

Jepsen, an independent tester, found in 2020 that PostgreSQL's Serializable mode could let through, in a rare case involving three transactions, an anomaly it should have blocked. The project fixed it that August, and the release notes describe the fix. The bug no longer exists; it shows that a guarantee is only as good as its implementation. The Jepsen report was read only in summary, so wording here follows the release notes.

The short answer

A transaction that is correct on its own usually works by reading some data, deciding something from what it read, and writing a result. When two such transactions run at the same time, the database may interleave their steps, so one of them can make its decision from a value the other is about to change. Each did the right thing with what it saw, yet together they produce a result that neither one-after-the-other order could have produced: a deposit disappears, money is withdrawn twice, or a rule like "someone must be on call" breaks.

Isolation levels are settings that tell the database how many of these harmful interleavings to forbid. The weakest levels forbid few and let transactions run freely. The strongest, serializable, forbids every interleaving whose result doesn't match some one-at-a-time order, and it pays for that by making transactions wait or by cancelling one so the application can retry it. The levels in between each close specific, named gaps, and the same level name can mean different things in different databases.

What a transaction promises

A transaction is a group of SQL statements that the database treats as one unit. You start it with BEGIN and end it with COMMIT, which makes its changes permanent, or ROLLBACK, which throws them all away. Until a transaction commits, its changes are provisional.

Data usually has rules it must always satisfy, called invariants: an account balance never goes below zero, a transfer leaves the total amount of money unchanged, at least one doctor is on call. Berenson and colleagues define a transaction as a group of actions that moves the database "from one consistent state to another." A transaction is individually correct when, run alone on data that satisfies the rules, it leaves data that still satisfies them. That is the "correct" in your question, and it is a property you can check one transaction at a time.

A database serves many connections at once. To keep them all moving, it does not wait for one transaction to finish before starting the next; it lets their statements run in between each other. Nothing is wrong with any single statement. Problems come from the order in which steps of different transactions land.

What "correct together" means

If transactions ran strictly one after another (a serial order), there would be nothing to worry about. Each starts from data that satisfies the rules and leaves data that satisfies them, so the next one also starts from good data, and so on down the line. Whichever order you pick, the end state is good.

That observation gives the reference definition of correct concurrent execution. An interleaved execution is serializable if its result equals the result of running the same transactions one at a time in some order. Berenson and colleagues put it formally: "A history is serializable if it is equivalent to a serial history." Ports and Grittner draw the consequence that matters in practice: if each transaction can be shown to do the right thing alone, it also does so in any serializable mix. You never have to reason about how your transaction interacts with someone else's.

So the precise version of your question is this: how can an interleaving produce a result that matches no serial order?

How two correct transactions produce a wrong result

Most of these bugs share one pattern, read-modify-write. The transaction SELECTs a value, the application computes something from it, and then the transaction UPDATEs the row with the computed result. Between the SELECT and the UPDATE there is a gap, and another transaction can change the value inside it.

Suppose an account holds 100. Transaction A deposits 20 and transaction B deposits 30, each by reading the balance and writing back the new total. Run A then B, and the balance goes 100 → 120 → 150. Run B then A, and it goes 100 → 130 → 150. Both serial orders end at 150. Now let the steps interleave:

StepTransaction A (+20)Transaction B (+30)Stored balance

Worked example built for this report from history H4 in Berenson et al. (1995), which uses the same numbers.

Both transactions committed, and the final balance is 130. A's deposit of 20 vanished, even though A was told it succeeded. Neither transaction made a mistake: each read the balance, added its amount, and wrote the sum. B's mistake, if you want to call it one, was deciding from a value that A changed after B read it. This failure is called a lost update. Berenson and colleagues write the same history in their compact notation (r = read, w = write, c = commit, digits name the transaction) as r1[x=100] r2[x=100] w2[x=120] c2 w1[x=130] c1, and conclude that "The final value of x contains only the increment of 30 added by T1."

The general ingredient is a conflict: two transactions touch the same data and at least one of them writes it. Conflicts force an order. Because B read 100 before A wrote 120, B has to come before A in any equivalent serial order. Because B's write of 130 replaced A's write, B also has to come after A. B cannot be both before and after A, so no serial order matches, and the result is wrong. Every anomaly in this report comes down to conflicts that pin the transactions into contradictory orders like this.

The same pattern takes money out. ACIDRain's opening example is a four-line withdrawal function that is correct when it runs alone.

    The named ways interleaving goes wrong

    Database researchers have named the recurring patterns, and isolation levels are described in terms of which ones they forbid. Each name describes a specific way one transaction can see or overwrite another's work at the wrong moment. The table collects them in one vocabulary; the descriptions are this report's summary of the definitions in Berenson et al. and the PostgreSQL manual.

    Write skew deserves a closer look, because it survives protections that stop every other item on the list. Ports and Grittner's example is a hospital rule that at least one doctor must be on call. Alice and Bob are both on call, and both feel unwell at the same moment.

    The doctors example matters because the conflict is hidden. In the deposit example both transactions wrote the same row, which a database can detect directly. Here each transaction read the rows the other wrote, but neither wrote what the other wrote. As Ports and Grittner put it, the write locks taken on update "don't solve this problem, because the two transactions modify different rows and thus do not conflict." Preventing it requires the database to track what each transaction read, not only what it wrote.

    Isolation levels: choosing which interleavings to forbid

    Forbidding interleavings has a cost. Every interleaving the database refuses means a transaction waits or is cancelled, so fewer transactions finish per second. Berenson and colleagues open their paper with the trade: running transactions at different isolation levels "allows application designers to trade throughput for correctness." Isolation levels are the menu for that trade.

    The SQL standard names four levels, from weakest to strongest: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, and SERIALIZABLE. It defines the lower three by which of three phenomena they must prevent: dirty reads, non-repeatable reads, and phantoms. PostgreSQL's manual reproduces that scheme and adds a column that matters.

    That last column is the main caveat about the standard. Berenson and colleagues showed that its definitions are both ambiguous and incomplete: they don't mention dirty writes, lost updates, or write skew at all, and a database that prevents the three named phenomena can still allow non-serializable results. They called it a common misconception that preventing those three phenomena gives serializability.

    Two ways a database enforces a level

    The first is locking. Before touching a row, a transaction takes a lock on it: a shared lock to read, an exclusive lock to write. A transaction that wants a conflicting lock waits until the holder releases it. In a locking database the levels differ mainly in how long read locks are held. At READ COMMITTED a read lock is released right after each read, so another transaction can change the row before you act on it. At REPEATABLE READ read locks on rows are held until commit, so nobody can change a row you have read. At SERIALIZABLE the database also locks the search condition itself, which blocks inserts that would match your WHERE clause. Write locks are held until commit at every level. Holding every lock until commit is called two-phase locking, and it gives serializability.

    The second is multiversion concurrency control, or snapshots. The database keeps older versions of rows, and a transaction reads a consistent picture of the data as of a particular moment, so readers never wait for writers. PostgreSQL's manual describes the result as "reading never blocks writing and writing never blocks reading." At Read Committed each statement gets a fresh snapshot, which is why two SELECTs in one transaction can disagree. Under snapshot isolation, the whole transaction reads from one snapshot taken at its first statement, and if two transactions write the same row, the first to commit wins and the other is refused. PostgreSQL, MySQL's InnoDB engine, and Oracle all work this way.

    Snapshot isolation stops dirty reads, non-repeatable reads, read skew, and lost updates. It does not stop write skew, because the doctors wrote different rows and the first-committer-wins check only compares writes. Berenson and colleagues' fuller table shows the result level by level.

    Each step up the ladder removes a class of interleavings. READ COMMITTED stops you from acting on changes that might be rolled back. REPEATABLE READ or snapshot isolation stops values from shifting under you in the middle of a transaction, and in PostgreSQL and in the paper's locking definition it also refuses lost updates (MySQL's version does not, as the next section shows). SERIALIZABLE also catches write skew and phantoms, which makes the result equal to some one-at-a-time order. That is the only level at which "each transaction is correct alone" is enough to guarantee correct results together.

    How SERIALIZABLE catches the doctors

    A locking database catches them by making each transaction hold read locks on the rows it counted. Bob's update must wait for Alice's transaction to release its locks, and with both waiting on each other the database cancels one. PostgreSQL's Serializable mode uses snapshots instead. It records which rows each transaction read, notices the pattern where each transaction read something the other later changed, and cancels one of them with an error. The PostgreSQL manual gives a similar case: one transaction sums class 1 (30) and inserts a row in class 2, while another sums class 2 (300) and inserts a row in class 1. At Repeatable Read both commit. At Serializable one fails with "could not serialize access due to read/write dependencies among transactions," because in either serial order one of the sums would have come out different.

    Two rows stand out. MySQL's default is called REPEATABLE READ, yet it let the lost update through; ACIDRain's authors reported being "surprised to trigger Lost Updates under MySQL Repeatable Read anyway." MySQL's manual explains part of why: plain SELECTs read from a snapshot, while UPDATEs act on the newest committed row, so a transaction can decide from an old value and write over a new one. Oracle's level called "serializable" behaved as snapshot isolation in Hermitage's tests, so it still allowed write skew. Knowing a level's name tells you less than knowing what it was tested to prevent.

    Defaults are also usually weaker than serializable. The current PostgreSQL manual states that "Read Committed is the default isolation level in PostgreSQL," and the current MySQL manual gives REPEATABLE READ as InnoDB's default. A January 2013 survey by Bailis and colleagues found that only 3 of 18 databases defaulted to serializable and 8 did not offer it at all. That survey covers old versions, but the current manuals show the pattern still holds for the two most common open-source databases. An application that never chooses a level gets the weaker protection.

    What the stronger levels cost

    A stronger level never makes a conflicting interleaving safe by magic. It either makes a transaction wait (locking) or cancels it with a serialization failure, an error that PostgreSQL reports with code 40001. Its manual is direct: "Applications using this level must be prepared to retry transactions due to serialization failures." Retrying means rolling back and running the whole transaction again from its first SELECT, so that it reads fresh values. Code that treats this error as a fatal failure will turn a correctness guarantee into user-visible errors.

    How much throughput the waits and retries cost depends on how the level is built and on the workload. Ports and Grittner measured PostgreSQL's snapshot-based serializable mode against snapshot isolation and against a classic locking implementation.

    On a second benchmark modeled on an auction site, the same paper reports 435 requests per second for snapshot isolation, 422 for SSI, and 208 for locking, with serialization failures of 0.004%, 0.03%, and 0.76% of transactions. The lesson is narrower than "serializable is cheap." In this one well-measured case, a modern serializable design cost a few percent, and an older design cost half.

    Limits: what isolation levels cannot do

    These bugs are not only theoretical. ACIDRain recounts the 2014 collapse of the Flexcoin Bitcoin exchange, whose own statement said an attacker, "By sending thousands of simultaneous requests," moved coins between accounts until the sender was overdrawn. The researchers then found 22 exploitable vulnerabilities in 12 popular e-commerce platforms, including reused gift cards and free items. Their breakdown says how much isolation levels could have helped.

    Isolation protects only what is inside one transaction. If an application reads in one transaction and writes in another, or with no transaction at all, no setting can reconnect the two, and raising the isolation level changes nothing. That was the more common bug in ACIDRain's sample by more than three to one.

    When an application stays at a weaker level, it can close specific gaps itself. Ports and Grittner list the usual tools, and the PostgreSQL manual and ACIDRain show them in use:

    • write the change as one atomic statement, such as UPDATE … SET balance = balance + 20, so no value passes through application code;
    • lock the rows you are about to decide from with SELECT … FOR UPDATE, which makes a concurrent transaction wait until you commit;
    • make a hidden conflict visible by writing a shared row both transactions must touch, such as a per-shift record in the doctors case;
    • let the database enforce the rule with a constraint, such as a check that a balance is not negative, so a violating write fails.

    Each of these fixes one known pattern. Their weakness is that someone has to find every pattern first. Ports and Grittner describe a court system with hundreds of tables and more than twenty programmers, where checking every pair of transactions for conflicts by hand was not feasible, and they note that these anomalies "typically manifest themselves as silent data corruption." That is the argument for choosing SERIALIZABLE and writing retry logic once, instead of hunting conflicts case by case.

    Finally, a guarantee is only as good as the code that implements it. In 2020 Jepsen's independent tests found a rare case in which PostgreSQL's serializable mode let an anomaly through; according to the release notes, the bug "could allow a serializable transaction to commit when it should have failed with a serialization error," and it was fixed that August. Tests like Hermitage's and Jepsen's can show that a database allows an anomaly, but no test can prove that it never will. Choosing a level, therefore, means checking what your specific database and version actually prevent, then deciding which of the remaining interleavings your application can tolerate.
