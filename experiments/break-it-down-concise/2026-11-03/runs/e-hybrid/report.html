The short answer

An eval is an automated test for behavior a unit test cannot check: run your assistant on fixed, realistic inputs, score each result with a grader, and count the passes. You need evals because model output varies between runs and a small prompt or model change can break things you were not watching. To start on a customer-support assistant, read about a hundred conversations, note what went wrong, group the notes into failure types, and turn the important types into pass/fail checks you re-run on every change.

Why normal testing is not enough

A unit test assumes the same input gives the same output. A model API breaks that twice: the same prompt can give different answers on different runs, and a correct reply to a customer is rarely one exact string. Without measurement, Anthropic's engineers write, teams wait for complaints and "can't distinguish real regressions from noise." Public leaderboards are model benchmarks comparing general models; what you need are product evals of your own prompts, tools, and code, a distinction Husain and Shankar draw.

What an eval is made of

A task (or test case) is one input plus its success criteria. A trial is one run on it; because outputs vary, you often run several. A grader scores the trial. The transcript (or trace) records every message and tool call, and the outcome is the resulting state of your system. A set of tasks is a suite.

The smallest eval is a loop you could write today, where reply is your assistant:

cases = [
    {"input": "I was charged twice for order 1042", "must_mention": "refund"},
    {"input": "Where is my package?", "must_call_tool": "lookup_order"},
    # ... 20 to 50 more, taken from real conversations
]
passed = 0
for case in cases:
    result = reply(case["input"])   # one trial
    ok = grade(case, result)        # True or False
    passed += ok
    log(case, result, ok)           # keep the transcript to read later
print(f"{passed}/{len(cases)} passed")

Three kinds of graders

Code

A rule: a regex match, valid JSON, the right tool called with the right arguments, the expected database row.

Fast and repeatable, but rejects correct answers phrased differently.

Model

An "LLM judge": a second model call asked one narrow question, such as "Did the reply follow the refund policy?"

Handles open-ended text, but varies and must be checked against people.

Human

A domain expert reads and labels outputs.

The reference standard, too slow to run on every change, so used to build and calibrate the other two.

Anthropic's rule is code where possible, a model where necessary, and humans to validate. Their illustrative refund task mixes them:

graders:
  - type: llm_rubric
    assertions:
      - "Agent showed empathy for customer's frustration"
      - "Agent's response grounded in fetch_policy tool results"
  - type: state_check
    expect:
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}

Abridged from Anthropic, "Demystifying evals for AI agents," "Example: Theoretical evaluation for a conversational agent."

Whether the refund happened is a database check; whether the tone fit needs a judge. The article also warns that demanding an exact tool-call sequence punishes valid routes you did not foresee, so grade the result where you can.

Start by reading conversations

Knowing what to check is the hard part, so Husain and Shankar put reading first:

"Error analysis is the most important activity in evals."

Husain and Shankar, AI Evals FAQ

Gather about 100 realistic conversations, written by you if you have no users yet. Write a free-form note on the first thing wrong in each (open coding), then group the notes into categories and count them (axial coding). Stop when new conversations stop revealing new failure types. Note anything that hurts the customer, even a missing tracking link the model had no tool to fetch, and write your rubric after reading, because what counts as good shifts once you see real conversations (criteria drift).

Turn failure types into pass/fail checks

Fix plain bugs once; for the remaining failure types, write one evaluator each with the cheapest grader that works. Husain and Shankar recommend pass or fail rather than 1–5 scores, because reviewers disagree on what separates a 3 from a 4 and drift to the middle. For partial credit, use several binary checks.

An LLM judge must be tested too

A judge can approach human consistency. In the MT-Bench study, GPT-4's choice of the better of two chat answers agreed with expert labelers 85% of the time (ties excluded), against 81% agreement between two humans. It also has habits. The best judge held its verdict only two-thirds of the time, and all leaned toward the first answer. The pairs were deliberately close, but the lesson holds: measure a judge before trusting it. Husain and Shankar have an expert label 100 to 200 examples per failure type, tune the judge's prompt on some, and test once on the rest, reporting the true positive rate, the share of real failures it catches (8 of 10 is 80%), and the true negative rate, the share of good replies it passes (95 of 100 is 95%).

For support, grade the outcome, repeatedly

A support assistant takes actions, so the most reliable grade is your system's end state, and it must succeed every time, not sometimes. In τ-bench a second model plays the customer from a hidden script, and each task allows only one correct final database state: the conversation can wander, the outcome cannot. The authors note this check would still miss, for example, a refund issued without the customer's confirmation.

For reliability they defined pass^k, the chance that all k tries at a task succeed, in contrast to pass@k, the chance that at least one does. A customer gets one try.

So run each case several times and count cases that passed every time: a case passing 75% of the time passes three runs in a row only 42% of the time (0.75³), as Anthropic notes. A simulated customer can wait; single messages from real tickets are enough to start.

How far to trust the score

Anthropic says "20-50 simple tasks drawn from real failures is a great start," since early changes have large effects. But your cases sample everything customers might send, so the pass rate is uncertain. Miller gives its standard error as roughly √(p(1−p)/n) for pass rate p over n cases: the uncertainty shrinks only with the square root of n. Try your own numbers:

With 40 cases, a true pass rate anywhere from 65% to 90% could plausibly produce an observed 80%.

95% Wilson score interval, a standard range for a proportion that stays sensible at small n and near 0% or 100%. Assumes independent, correctly graded cases; a biased grader shifts the whole range.

At 40 cases, 80% is compatible with anything from 65% to 90%, so a move to 85% proves nothing alone. Miller recommends comparing versions case by case on the same set; at small n, read the cases that flipped.

Keeping it honest

Capability evals target what the assistant does badly and start with low pass rates; regression evals cover what already works and should pass nearly always. Every new production failure becomes a case. Keep reading transcripts, since graders have bugs too: Anthropic reports one that marked "96.12" wrong for not matching "96.124991…". And evals catch only what you thought to test, so Anthropic pairs them with production monitoring, user feedback, and A/B tests.

Two limits apply. The numbers here come from 2023–2024 models and simulated stores, so current models will score differently, though the variability and judge biases they show are why these methods exist. And the starting sizes and pass/fail preference are practitioners' defaults, not controlled findings; adjust them when your own data disagrees.
