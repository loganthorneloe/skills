The short answer

An eval is an automated test for behavior you cannot check with a normal unit test: you run your assistant on a fixed set of realistic inputs, score each result with a grader, and count how often it passes. You need evals because a model's output varies from run to run and a small prompt or model change can break things you were not looking at. To start on a customer-support assistant, read a hundred or so real or simulated conversations, write down what went wrong, group those notes into failure types, and turn the most important types into pass/fail checks that you re-run on every change.

Why normal testing is not enough

A normal test assumes the same input always gives the same output, so you can assert on it. A model API breaks that assumption twice. First, the same prompt can produce different answers on different runs, so one passing run tells you little. Second, the "correct" answer to a customer's message is usually not one exact string; many phrasings are fine and some subtly wrong ones look fine.

Without a way to measure, teams fall into what Anthropic's engineers describe as reactive loops: wait for complaints, reproduce by hand, fix, and hope nothing else broke. Their article says teams without evals "can't distinguish real regressions from noise" and cannot test a change against hundreds of scenarios before shipping. The same problem appears when a new model is released: Anthropic reports that teams with evals can assess and adopt a new model in days, while teams without them face weeks of manual testing.

Public leaderboards do not fill this gap. Husain and Shankar separate model benchmarks, which compare general models on shared tasks, from product evals, which check whether your system, including your prompts, tools, and code, does what your users need. A benchmark score says nothing about whether your assistant picked the right order before cancelling it.

What an eval is made of

Anthropic's article defines a small set of parts. A task (also called a test case) is one input plus the criteria for success. A trial is one run of your system on that task; because outputs vary, you often run several. A grader is the logic that scores a trial. The transcript (or trace) is the full record of the trial: every message, tool call, and intermediate result. The outcome is the final state of the world afterward, such as whether a refund record exists in your database. A collection of tasks is a suite.

That distinction matters for support. A support assistant that says "Your refund has been processed" may not have processed anything. Anthropic's example is a flight-booking agent: the outcome is not the sentence "Your flight has been booked" but whether the reservation exists in the database.

In code, the smallest possible eval is a loop you could write today. Suppose your assistant is a function reply(conversation) that calls a model API:

cases = [
    {"input": "I was charged twice for order 1042", "must_mention": "refund"},
    {"input": "Where is my package?", "must_call_tool": "lookup_order"},
    # ... 20 to 50 more, taken from real conversations
]

passed = 0
for case in cases:
    result = reply(case["input"])        # one trial
    ok = grade(case, result)             # True or False
    passed += ok
    log(case, result, ok)                # keep the transcript to read later

print(f"{passed}/{len(cases)} passed")

Everything else in this report is about filling in that loop well: which cases go in cases, what grade should check, and how to read the number at the end.

Three kinds of graders

The grader is where most of the judgment lives. Anthropic groups graders into three kinds, and Husain and Shankar draw the same line between checks a rule can decide and checks that need judgment.

Code

A rule your program checks: an exact or regex match, valid JSON, the right tool called with the right arguments, the expected row in the database.

Fast, cheap, and repeatable, but brittle to correct answers phrased differently.

Model

A second model call (an "LLM judge") asked a narrow question about the output, such as "Did the reply follow the refund policy?"

Handles open-ended text, but is itself variable and must be checked against people.

Human

A person who knows the domain reads and labels outputs.

The reference standard, but slow and expensive, so mostly used to build and calibrate the other two.

Anthropic's advice is to use code graders where possible, model graders where necessary, and humans to validate. A single support task often mixes them. Their illustrative refund task for a frustrated customer combines:

graders:
  - type: llm_rubric
    assertions:
      - "Agent showed empathy for customer's frustration"
      - "Resolution was clearly explained"
      - "Agent's response grounded in fetch_policy tool results"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10

Excerpt from Anthropic, "Demystifying evals for AI agents," section "Example: Theoretical evaluation for a conversational agent."

Notice the division of labor: whether the refund happened is a database check, whether the tone was right needs a judge. The same article cautions against requiring an exact sequence of tool calls, because a capable assistant may find a valid route the test writer did not anticipate; grade what was produced, not the path, where you can.

Start by reading conversations, not writing tests

The hardest part is not the loop but knowing what to check. Husain and Shankar put it bluntly:

"Error analysis is the most important activity in evals."

Husain and Shankar, AI Evals FAQ

Error analysis means reading traces and writing down what goes wrong before deciding what to measure. Their process has four steps. Gather a set of representative conversations; if you have no users yet, write or generate realistic customer messages. Read each one and write a free-form note about the first thing that looks wrong, which qualitative researchers call open coding. Group the notes into categories, called axial coding, and count how many fall in each. Keep reading until new conversations stop revealing new kinds of failure. They suggest a pool of about 100 diverse traces, with at least the first 30 annotated by hand before letting any tool suggest failures.

Two of their points matter for a support assistant. Write down anything that makes the product worse, even if the model is not at fault: their example is an assistant that says an order has shipped without giving a tracking link because it has no tool to fetch one. And do not write a rubric before you read; what you consider "good" shifts once you see real conversations, a change they call criteria drift. You might only discover by reading that your policy of escalating refunds to a human is frustrating customers.

The τ-bench authors did exactly this kind of analysis on failed support conversations. They ran a gpt-4o assistant on 115 simulated retail tasks, read the 40 failures, found 4 caused by mistakes in the test itself, and sorted the remaining 36:

Turn each failure type into a pass/fail check

Once you have failure types, write one evaluator per important type. Husain and Shankar recommend that each return pass or fail rather than a 1–5 score. Their reasoning is that the difference between a 3 and a 4 is inconsistent between reviewers, reviewers drift to the middle to avoid hard calls, and scales need more examples to show a real difference. If you want partial credit, split the score into several binary checks, such as "4 of 5 required facts present."

Many failures will turn out to be plain bugs you fix once without any evaluator. For the rest, choose the cheapest grader that works. "Did it call lookup_order with the order number the customer gave?" is a code check. "Did it refuse a refund the policy allows?" probably needs a judge. To report one number, they suggest a pass-all rate, the share of cases that pass every check, with the ability to drill down to each check.

An LLM judge is a model you must test too

A judge is attractive because it scales, and it can be accurate. In the MT-Bench study, GPT-4's verdicts on which of two chat answers was better agreed with expert human labelers 85% of the time (ties excluded), slightly more than the 81% at which two humans agreed with each other. That was general chat in 2023, not support policy, but it shows a judge can approach human consistency.

Even the best judge kept its verdict only about two-thirds of the time when nothing changed but the order, and most leaned toward whichever answer came first. The answer pairs were deliberately close, and consistency is not the same as accuracy, but the lesson carries over: a judge has its own habits. The paper also found judges preferred answers padded with a rephrased repeat of the same list.

So treat a judge like any classifier and measure it. Husain and Shankar's method is to have a domain expert label examples pass or fail (they suggest 100 to 200 per failure type), tune the judge's prompt on part of them, and test it once on a held-out part. Report two numbers. The true positive rate is how many real failures the judge catches: if people found 10 failures and the judge flagged 8, that is 80%. The true negative rate is how many good replies it correctly passes: 95 of 100 is 95%. Anthropic adds practical guards: ask the judge one narrow question per call, and give it a way to answer "unknown" instead of guessing.

For a support assistant, check the outcome and check it repeatedly

Support conversations have two features that shape their evals. The assistant takes actions, such as refunds and cancellations, so the most reliable grade is the end state of your system. And customers are many and varied, so the assistant must succeed reliably, not occasionally.

τ-bench handles both. A second model plays the customer from a hidden script ("You want to return the water bottle and exchange the pet bed…"), and the assistant uses real-looking order tools and a written store policy. Each task is written so that only one final database state is correct under the policy, so grading is a comparison of the database against that state plus a check that the reply contained required facts. The conversation can wander; the outcome cannot. The authors note this check is necessary but not sufficient, since it would miss, for example, a refund issued without the customer's confirmation.

To measure reliability, they introduced pass^k: the chance that all k independent tries at the same task succeed. It contrasts with pass@k, the chance that at least one of k tries succeeds, which suits tasks where you can pick the best of several attempts. A customer gets one attempt.

For your own assistant, this means running each test case several times and reporting how many cases passed every time, not just the average. If an assistant passes a refund case 75% of the time, the chance it passes three runs in a row is about 0.75³, or 42%, the arithmetic Anthropic uses to make the same point.

You do not need a full simulated store to begin. Your first support suite can be single customer messages from real tickets, each with a code check on the tool call or a judge check on the reply. Add a simulated customer later for multi-turn flows such as "change my address on all my orders," where τ-bench found assistants often stopped after the first order.

How many cases, and how much to trust the score

Anthropic's article says teams wait too long because they think they need hundreds of tasks, when "20-50 simple tasks drawn from real failures is a great start." Early changes tend to have large effects, which a small set can detect. The catch is that a score from a small set is itself uncertain: the cases you happened to pick are a sample of all the messages customers could send.

Miller's paper makes this explicit. Treat each case as a draw from a larger population of possible questions, and the pass rate has a standard error of roughly √(p(1−p)/n), where p is the pass rate and n the number of cases. The error shrinks only with the square root of n, so quadrupling your cases halves the uncertainty. The calculator below shows the 95% range for the true pass rate given your numbers.

Uses the Wilson score interval, a standard 95% interval for a proportion that stays sensible for small n and rates near 0% or 100%. Assumes cases are independent and graded correctly; a biased grader shifts the whole range.

At the defaults, an 80% score on 40 cases is compatible with anything from the low 60s to about 90%. A change from 80% to 85% on that set is not evidence of improvement by itself. Miller's recommendation for comparing two versions is to run both on the same cases and look at the case-by-case differences, which removes much of the noise from case difficulty. In practice, at small n, read the cases that flipped from fail to pass or back rather than trusting the headline number.

Keep the suite alive

Anthropic distinguishes two uses of the same machinery. Capability evals target things the assistant does poorly and should start with a low pass rate, giving you something to improve. Regression evals cover what already works and should pass nearly 100%; a drop means something broke. Cases graduate from the first to the second as you fix them. Every new failure found in production becomes a new case, so the suite grows from real problems rather than imagined ones.

Read transcripts regularly, including for passing cases. Anthropic reports scores that were wrong because of the grader, not the model: one benchmark marked "96.12" wrong because it expected "96.124991…", and fixing grading bugs like that, along with loosening the test setup, moved one model from 42% to 95%. A failing case should fail for a reason you can see.

Finally, automated evals are one layer. Anthropic lists production monitoring, user feedback such as thumbs-down, A/B tests on real traffic, and human review as complements: evals catch problems before users do, while monitoring and feedback catch the problems your test cases never imagined.

What this means for your first week

The practical consequence is that your first eval work is reading, not infrastructure. Collect 50 to 100 support conversations, real or written by you, run your assistant on them, and annotate what went wrong. The failure types you find decide which checks to write, starting with code checks on tool calls and database outcomes, adding a judge only where a rule cannot decide, and validating that judge against your own labels. Run each case more than once, and treat small score changes on a small suite as a prompt to read transcripts, not as proof.

Two limits remain. The specific numbers here come from 2023–2024 models and simulated stores; today's models will score differently, though the variability and judge biases they illustrate are why the methods exist. And the starting sizes and the preference for pass/fail checks are experienced practitioners' advice rather than results of controlled studies; treat them as defaults to adjust once your own data says otherwise.
