ACIDRain: Concurrency-Related Attacks on Database-Backed Web Applications↗

Todd Warszawski and Peter Bailis · Conference paper, ACM SIGMOD · May 2017

Stanford researchers confirmed each vulnerability by triggering it against real e-commerce software. Some attacks needed an added network delay to trigger reliably.

Each operation is correct only if nothing changes the data between its read and its write. When two run at once, the database interleaves their steps, so one can act on a value the other is about to change, and the result matches no order of running them one after the other. Isolation levels tell the database which interleavings to forbid; only Serializable forbids all of them, and it does so by making transactions wait or fail and retry.

What “correct” means when transactions overlap

Correct together means equivalent to some one-at-a-time order. A transaction is a group of SQL statements between BEGIN and COMMIT that the database treats as one unit. Each transaction is written to keep the data's rules, called invariants, such as “a balance never goes below zero.” If every transaction keeps the rules when it runs alone, then running them one after another in any order keeps the rules too. So the reference definition, called serializability, asks only that the result equal some such order.

The general mechanism is a conflict: two transactions touch the same data, at least one writes it, and one acts on a value the other changes. The withdraw race is a lost update: Berenson and colleagues give the same pattern with additions, where a balance of 100 receives +20 and +30 but ends at 130 instead of 150. Other recurring patterns have names too:

  • a dirty read sees another transaction's change before it commits, when it may still be undone;
  • a non-repeatable read reads the same row twice and gets two values;
  • a phantom repeats a WHERE search and gets a different set of rows;
  • write skew has two transactions each check a rule and then change different rows, breaking the rule together.

Isolation levels forbid classes of interleaving

Each stronger level rules out more of these patterns, at the price of more waiting or more failed transactions. The SQL standard names four levels and defines them by three of the patterns. PostgreSQL's manual reproduces that table and adds a column.

Read the last column. “Serialization anomaly” stays possible at every level except Serializable, which is the practical form of Berenson and colleagues' main finding: blocking the standard's three named patterns does not make execution serializable, and lost updates and write skew fall outside them. “Allowed, but not in PG” marks where PostgreSQL is stricter than the standard requires.

Databases enforce these levels in two main ways. With locks, a transaction locks each row it touches and conflicting requests wait; holding every lock until commit gives serializability, and releasing read locks early gives weaker levels. With snapshots, the database keeps old row versions so each transaction reads a consistent picture of the past. PostgreSQL's Repeatable Read is this second design, known as snapshot isolation.

Snapshots still miss write skew

Snapshot isolation stops lost updates because two transactions writing the same row collide, but write skew writes different rows, so nothing collides. Ports and Grittner's example has a hospital rule that at least one doctor stays on call.

Alone, either transaction leaves a doctor on call. Together they leave none, and because Alice's row and Bob's row are different, the snapshot design sees no conflict. Only Serializable catches this. PostgreSQL's version notices that each transaction read data the other changed, a pattern no one-at-a-time order can produce, and rolls one back with a “could not serialize access” error. The manual says applications at this level “must be prepared to retry transactions due to serialization failures.” In Ports and Grittner's benchmarks this cost less than 7% of throughput compared with snapshot isolation, while a traditional locking design ran at under half the speed on read-heavy work.

The same name can mean different guarantees

A level's name tells you less than its tested behavior. Hermitage's tests found that PostgreSQL's Repeatable Read prevents lost updates while MySQL's Repeatable Read does not, and ACIDRain's authors reported the same surprise. Hermitage also classifies Oracle's “serializable” as snapshot isolation. Defaults sit below Serializable too: PostgreSQL defaults to Read Committed and MySQL to Repeatable Read, so most applications get full protection only if they request it.

What isolation cannot fix

Isolation protects only steps inside one transaction. ACIDRain confirmed 22 exploitable bugs in 12 e-commerce platforms, including repeated gift-card spending. Five came from weak default levels. The other 17 came from code that never grouped its steps into a transaction, which no level can repair. At weaker levels, specific gaps can be closed by hand. A single statement such as UPDATE accounts SET balance = balance - 99 WHERE id = 1 AND balance >= 99 leaves no gap between read and write, because PostgreSQL re-checks the condition against the newest committed row. SELECT … FOR UPDATE locks the rows read so a competitor waits, and database constraints refuse invalid data outright. Each fix covers one known conflict, which is why Ports and Grittner argue for Serializable on large systems where checking every pair of transactions by hand is impractical.
