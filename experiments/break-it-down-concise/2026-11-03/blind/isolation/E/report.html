The short answer

Each operation is correct alone, but a database interleaves the steps of many operations at once. If one reads a value and another changes it before the first finishes acting on what it read, the first acts on stale information, and the combined result can match no order in which they could have run one at a time. That is the definition of wrong. Isolation levels are rules about which interleavings the database allows. Weaker levels allow more in return for less waiting. Serializable allows only results equivalent to some one-at-a-time order, enforced by making transactions wait or cancelling one for the application to retry. Most databases do not default to it, and the same level name means different things in different products.

What "correct" means

A transaction is a group of SQL statements, from BEGIN to COMMIT, that the database treats as one unit. It is correct when, run alone, it keeps the data's rules true, such as a balance never going negative. Most logic follows one pattern: SELECT a value, decide or calculate in application code, then UPDATE with the result.

Run correct transactions one after another and every result is correct, because each starts from valid data and leaves valid data behind. So the reference definition of correct concurrent execution, serializability, asks only that the result equal some one-at-a-time order. In Berenson and colleagues' words, an execution "is serializable if it is equivalent to a serial history." Databases do not actually run transactions one at a time, though; they interleave statements from many connections so none waits for the others.

How two correct operations produce a wrong result

Suppose an account holds 100. Transaction A adds 20 and B adds 30, each by reading the balance and writing back a new total. Either order run alone ends at 150. Now let the steps interleave.

Both committed, and A's 20 vanished, because B computed its total from a value A had already replaced. This is a lost update; Berenson and colleagues give the same history and conclude that the final value "contains only the increment of 30." The mechanism is a conflict: two transactions touch the same item, at least one writes it, and so one acts on a value the other changes. B must come before A, because B read the old value, and after A, because B overwrote A's write. No serial order satisfies both.

The same pattern moves money out. Warszawski and Bailis show it with a withdraw function.

Grouping steps into a transaction does not by itself stop another transaction reading the same balance in between.

    Play the bad order at each level. Read Committed silently ends at 130. Repeatable Read makes B's write fail; retrying lets B read 120 and finish at 150. The stronger level did not compute the right answer; it refused the wrong one and handed the work back to the application. Running all of A before B gives 150 at both levels, so the bug appears only with an unlucky overlap. One practical exception: a single statement such as UPDATE accounts SET balance = balance + 20 does not lose the update at PostgreSQL's Read Committed, because the second UPDATE waits and then adds to the newly committed value. The bug needs the value to pass through application code.

    How isolation levels help

    Preventing every bad interleaving costs waiting or cancelled work. Berenson and colleagues' opening sentence states the bargain: isolation levels let designers "trade throughput for correctness." The SQL standard names four levels, Read Uncommitted, Read Committed, Repeatable Read, and Serializable, and defines the lower three by which of three anomalies each forbids: dirty reads (reading another transaction's uncommitted write), non-repeatable reads (a row changing between two reads), and phantoms (a repeated WHERE search returning different rows). Berenson and colleagues showed that forbidding these three is not serializability, because lost updates, dirty writes, and write skew fall outside them. Their fuller table places each level against all of these.

    Moving down the table generally forbids more. Read Committed allows the lost update; Repeatable Read and Snapshot prevent it. Snapshot and Repeatable Read each leave a different gap, phantoms in one and write skew in the other, and only Serializable reads "Not Possible" everywhere. "Repeatable Read" here is the paper's locking definition, which products do not all follow.

    Databases enforce levels in two main ways. With locks, a transaction locks rows before touching them and conflicting requests wait; holding every lock until commit gives serializability, and releasing read locks early gives weaker levels. With snapshots, the database keeps old row versions so each transaction or statement reads a consistent past state without blocking writers, while writers still lock the rows they change. PostgreSQL, Oracle, and MySQL's plain reads use snapshots, and PostgreSQL's manual says its Repeatable Read "is implemented using ... Snapshot Isolation."

    The gap snapshots leave

    Write skew happens when two transactions read overlapping data, each checks a rule, and each writes a different row. Ports and Grittner's example has the rule that at least one doctor stays on call.

    Both transactions count two doctors from the same snapshot, so both go off call. They update different rows, so, as the authors say, the write locks "don't solve this problem." Both commit and nobody is on call, though either order run alone would have stopped the second. PostgreSQL's Serializable mode catches this by watching for the pattern of read and write dependencies and cancelling one transaction; a locking database holds each transaction's read locks until commit, so the two conflicting writes block and one transaction must wait or be cancelled. At weaker levels, SELECT ... FOR UPDATE on the counted rows closes this one gap.

    "Repeatable read" stops lost updates in PostgreSQL but not in MySQL, where the ACIDRain authors were also "surprised to trigger Lost Updates." Oracle's "serializable" is snapshot isolation by these tests. Defaults are weak too: the current manuals give Read Committed for PostgreSQL and Repeatable Read for MySQL, and in a January 2013 survey only 3 of 18 databases defaulted to serializability.

    What protection costs

    Stronger levels block or abort, so, in PostgreSQL's words, "applications using this level must be prepared to retry transactions due to serialization failures." The throughput cost depends on implementation and workload. Ports and Grittner measured an auction-site benchmark.

    PostgreSQL's serializable mode kept about 97% of snapshot isolation's throughput, while lock-based serializable managed under half and aborted more. The authors' broader figure is a cost "less than 7%." This is PostgreSQL 9.1 on 2012 hardware against a locking version they built themselves, so full protection can be cheap but is not always.

    What isolation cannot fix

    Isolation protects only what is inside one transaction. Of ACIDRain's 22 vulnerabilities, such as repeated gift-card spending, 5 came from weak default isolation and 17 from code that never put the read and the write in one transaction, which no level can repair. Applications can also close specific gaps directly with single-statement updates, SELECT ... FOR UPDATE, or database-enforced constraints, but each fixes one known pattern. And a guarantee is only as good as its code: PostgreSQL 12.4's release notes record a fixed bug that "could allow a serializable transaction to commit when it should have failed." So put each read-decide-write sequence in one transaction, learn what your database's level actually means, and use Serializable with retries, or explicit locks, where a rule spans rows.
