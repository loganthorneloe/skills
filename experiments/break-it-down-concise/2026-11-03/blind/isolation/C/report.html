Database transaction isolation.

Sources

A Critique of ANSI SQL Isolation Levels↗

Hal Berenson, Phil Bernstein, and colleagues · Conference paper and Microsoft Research technical report, ACM SIGMOD · June 1995

This paper pinned down what the SQL standard's isolation levels actually guarantee. Its authors include Jim Gray, who won the Turing Award for transaction processing, and Jim Melton, editor of the SQL standard. They write out exact sequences of reads and writes and show which ones each level lets through, proving that the standard's plain-English rules leave holes. It also gave the first precise definition of snapshot isolation. Its arguments are logical proofs rather than measurements, so they still hold, but its descriptions of 1995 products do not describe today's versions. A later rework of its definitions (Adya and colleagues, 2000) supplies the vocabulary that testing tools such as Hermitage use.

PostgreSQL 18 Documentation: Transaction Isolation↗

The PostgreSQL Global Development Group · Official product documentation, postgresql.org · Current manual, accessed November 2026

The developers of PostgreSQL wrote this page to say exactly what each level does in the current release. It gives the standard's four levels in a table, short SQL examples of what goes wrong at each, and the error a transaction receives when the database refuses a conflicting interleaving. It confirms that Read Committed is PostgreSQL's default, that its Repeatable Read is snapshot isolation, and that its Serializable level aborts one transaction of a conflicting pair, which the application must retry. It describes only PostgreSQL.

MySQL 8.4 Reference Manual: Transaction Isolation Levels↗

Oracle Corporation · Official product documentation, dev.mysql.com · MySQL 8.4 manual, accessed November 2026

MySQL's manual for its main storage engine, InnoDB, in the current long-term-support release. It confirms that the default level is Repeatable Read, and it explains the source of that level's surprises: plain SELECTs read from a snapshot, while UPDATEs and locking reads act on the newest committed data. The vendor calls the default strongly consistent, but independent tests (Hermitage, ACIDRain) found it lets lost updates through, so read it alongside them.

Serializable Snapshot Isolation in PostgreSQL↗

Dan R. K. Ports and Kevin Grittner · Conference paper, Proceedings of the VLDB Endowment (VLDB 2012) · August 2012

The two engineers who built PostgreSQL's Serializable mode explain how it works and measure what it costs. Its two-doctors example shows plainly why snapshot isolation is not enough. Their benchmarks ran on 2012 hardware and PostgreSQL 9.1, against a locking implementation they built themselves for comparison, so the numbers are one measured case rather than a general rule. An independent tester found a bug in this mechanism in 2020; it has been fixed.

Highly Available Transactions: Virtues and Limitations↗

Peter Bailis, Aaron Davidson, and colleagues · Conference paper (extended version), VLDB 2014 / arXiv · February 2013

Only one table from this paper is used here: a survey of the default and strongest isolation levels in 18 databases as of January 2013, compiled by database researchers from vendor documentation. It is a historical snapshot of old versions, and some of the products no longer exist. It supports the general point that weak defaults are normal, which the current PostgreSQL and MySQL manuals still confirm, but not any one database's current default.

ACIDRain: Concurrency-Related Attacks on Database-Backed Web Applications↗

Todd Warszawski and Peter Bailis · Conference paper, ACM SIGMOD · May 2017

Stanford researchers tested whether real shopping software breaks when an attacker sends many requests at once, and confirmed 22 such vulnerabilities in 12 popular e-commerce platforms. Five came from the database's default isolation level; the other 17 came from code that never grouped its steps into one transaction, which no isolation level can fix. The "2 million websites" figure counts sites running the affected software, not sites attacked, and some attacks needed an added network delay to trigger reliably.

Hermitage: Testing Transaction Isolation Levels↗

Martin Kleppmann and contributors · Open test suite and results, GitHub · First published November 2014, updated January 2026

Each test is a step-by-step script for two database sessions that tries to trigger one specific anomaly, so anyone can rerun it and check the result. Its summary table compares what each database calls a level with what that level actually prevents. The tests were run by hand on particular versions, some old (the PostgreSQL scripts used 9.3.5); they can show an anomaly happens but cannot prove it never will. The PostgreSQL results agree with the current manual.

PostgreSQL 12.4 Release Notes↗, with Jepsen: PostgreSQL 12.3↗

The PostgreSQL Global Development Group · Release notes · August 2020; Kyle Kingsbury · Independent consistency analysis, jepsen.io · June 2020

Jepsen, an independent tester, found in 2020 that PostgreSQL's Serializable mode could let an anomaly through in a rare case involving three concurrent transactions. The project fixed it in its August 2020 releases. The Jepsen report was read only in summary, so the wording quoted here comes from the release notes. The bug no longer describes current behavior.

The short answer

A transaction is usually a read followed by a write that depends on what was read. Each one is correct when it runs alone. When two run at once, the database may run their steps interleaved, so one transaction can make its decision from a value the other is about to change. Both then commit, and the result matches neither one-after-the-other order: money is added once instead of twice, or a rule that each transaction checked ends up broken. An isolation level is the setting that tells the database which of these interleavings to refuse. Weaker levels refuse fewer and run faster. Only serializable refuses every interleaving whose result could not have come from running the transactions one at a time, and it does so by making a transaction wait or by aborting it so the application can retry.

What a transaction promises

A transaction is a group of SQL statements between BEGIN and COMMIT that the database treats as one unit. Berenson and colleagues define it as a group of actions that moves the database "from one consistent state to another." Consistent here means the data obeys its rules, which are called invariants: a balance never goes below zero, at least one doctor is on call, a transfer leaves the total amount of money unchanged.

A transaction is individually correct if, run alone against data that obeys the rules, it leaves data that still obeys them. That is a property each programmer can check by reading one piece of code. The trouble is that a database serves many connections at once. To stay fast, it lets steps from one transaction run between steps of another. No single statement does anything wrong; what can go wrong is the order in which steps from different transactions land.

What "correct together" means

Suppose the database ran transactions strictly one after another, with no overlap. That is called a serial order. If every transaction is correct alone, every serial order is correct too, because each transaction starts from good data and leaves good data for the next one. So the reference definition of correct concurrent execution is: the result must equal the result of some serial order. The paper that set out these definitions puts it in one line:

"A history is serializable if it is equivalent to a serial history."

A history is the actual sequence of reads, writes and commits the database performed. An execution with that property is serializable. Ports and Grittner state why it matters: if each transaction does the right thing alone, a serializable database guarantees it also does the right thing in any mix. Every isolation level below serializable gives up part of that guarantee.

How two correct transactions produce a wrong result

The most common shape of a bug is read-modify-write: SELECT a value, compute or decide something in application code, then UPDATE based on what was read. Between the SELECT and the UPDATE, another transaction can change the value, so the decision is made from stale data.

The ACIDRain paper opens with four lines of exactly this kind. Read the balance, check that it covers the withdrawal, write the reduced balance. Run once, the function never overdraws.

Look at the gap between line 2 and line 4 of version (a). Two calls with a $100 balance can both read $100, both pass the check that $100 is at least $99, and both write $1. Each call behaved correctly given what it read, yet $198 left an account that held $100. The caption makes the second point that matters here: putting the steps in a transaction, as version (b) does, still does not stop this at Read Committed or below unless the code takes an explicit lock.

The same failure, step by step

Berenson and colleagues write this failure as a precise sequence they call H4, using a value x that starts at 100. Transaction 2 adds 20 and transaction 1 adds 30:

H4: r1[x=100] r2[x=100] w2[x=120] c2 w1[x=130] c1

Here r1[x=100] means "transaction 1 reads x and sees 100," w is a write and c is a commit. Both read 100 before either writes. Transaction 2 writes 120 and commits; transaction 1 then writes 130, computed from its stale 100. In the paper's words, "The final value of x contains only the increment of 30 added by T1." Run in either serial order, x would end at 150. Transaction 2's addition vanished even though it committed. This is a lost update.

The general cause is a conflict: two transactions touch the same data item and at least one of them writes it. A read-modify-write turns a conflict into a bug because one transaction acts on a value that the other changes before the first one finishes.

The Hermitage suite shows the same thing in plain SQL across two database sessions. Both sessions start at Read Committed, both read row 1 (value 10), and each decides to write 11, as an application adding 1 to what it read would:

begin; set transaction isolation level read committed; -- T1
begin; set transaction isolation level read committed; -- T2
select * from test where id = 1; -- T1
select * from test where id = 1; -- T2
update test set value = 11 where id = 1; -- T1
update test set value = 11 where id = 1; -- T2, BLOCKS
commit; -- T1. This unblocks T2, so T1's update is overwritten
commit; -- T2

Two increments produce 11, not 12. Notice the row lock did make T2 wait, but waiting did not help: when T2 resumed, it wrote a value it had already computed from the old read. Run the same steps at PostgreSQL's Repeatable Read and T2 instead receives ERROR: could not serialize access due to concurrent update and is rolled back.

One detail changes how you write such code. If the addition happens inside a single statement, UPDATE accounts SET balance = balance + 20 WHERE …, PostgreSQL's Read Committed does not lose the update. The second UPDATE waits for the first to commit, then re-reads the newly committed row and adds to it. The bug needs the value to pass through application code between a SELECT and an UPDATE.

Try every interleaving

Transaction A adds 20 and transaction B adds 30 to a balance of 100, each by reading the balance and then writing read value plus its amount. Each step keeps its own transaction's order (read before write), so there are six possible orders. Choose an order and a level to see what the database does.

  2. Breads balance100
  3. Awrites 100 + 20, commits120
  4. Bwrites 100 + 30, commits130

Final balance 130Wrong: A's +20 was lost

Both serial orders end at 150. This interleaving matches neither.

The model assumes each transaction commits right after its write, and the write uses a value computed in application code from the earlier SELECT (the Hermitage pattern), not balance = balance + n. Behavior per level follows the Hermitage lost-update tests and the PostgreSQL 18 manual: Read Committed and MySQL Repeatable Read let the stale write through; PostgreSQL Repeatable Read and Serializable abort the second writer with a serialization failure, which the application retries from the start.

Four of the six orders lose an update at the default level of both databases. In every one of the four, both reads happen before either write, so one transaction writes a total computed from a balance that is already out of date. Switching the level to PostgreSQL Repeatable Read does not make the bad orders impossible; it makes the database notice them and abort the late writer, and the retry, now reading 120 or 130, produces 150.

A failure where no row is shared

A lost update involves two writes to the same row, so a database can catch it by watching that row. A subtler failure, write skew, needs no shared write at all. Ports and Grittner's example has a hospital rule that at least one doctor must be on call. Alice and Bob are both on call, and each tries to go off call at the same moment.

Each transaction counts the on-call doctors, sees 2, and so takes one doctor off. Either one alone leaves one doctor on call, and run one after the other the second would see a count of 1 and change nothing. Run together, both see 2, and the hospital ends with nobody on call. The paper explains why ordinary row locking misses it: "The write locks taken on update don't solve this problem, because the two transactions modify different rows and thus do not conflict." T1 wrote Alice's row and T2 wrote Bob's, but each had read the row the other changed.

That gives a general way to see when a result is wrong. Draw each transaction as a node and add an arrow from one to another whenever the first must come before the second in any equivalent serial order. If T2 read the old version of a row T1 later wrote, T2 must come first, because in a serial order where T1 ran first T2 would have seen T1's write.

In panel (a) the doctors example forms a loop: T1 must come before T2, and T2 must come before T1. No serial order satisfies both, so the outcome is not serializable. Any non-serializable outcome, including the lost update above, shows such a loop when drawn this way. PostgreSQL's Serializable level works by watching for the start of such loops and aborting one transaction before the loop can close.

The named failure patterns

Researchers have named the interleavings that keep recurring. The names matter because isolation levels are defined, and documented, by which of them they prevent. This plain-language summary follows Berenson and colleagues' list, which added dirty write, lost update, read skew and write skew to the three the SQL standard names.

NameWhat happens
Dirty writeA transaction overwrites another's write before that one has committed.
Dirty readA transaction reads another's uncommitted write, which might still be rolled back and so never officially exist.
Non-repeatable (fuzzy) readA transaction reads the same row twice and gets different values, because another transaction changed and committed it in between.
PhantomA transaction repeats a search (a WHERE condition) and gets a different set of rows, because another inserted or deleted matching rows.
Lost updateTwo read-modify-writes on the same row; the later write erases the earlier one, as in H4.
Read skewA transaction reads two related rows at different moments and sees a mix of before and after, such as half of a transfer.
Write skewTwo transactions read overlapping data, each checks a rule, and each writes a different row; together they break the rule, as with the doctors.

Synthesis of definitions in Berenson et al. (1995) and the PostgreSQL 18 manual. Hermitage uses a later, more formal vocabulary for some of the same patterns: P4 for lost update, G-single for read skew and G2-item for write skew.

Read skew is worth one concrete case, because it needs no write conflict at all. In Berenson and colleagues' history H1, transaction 1 moves 40 from account x (50) to account y (50), keeping the total at 100. A reporting transaction reads x after the withdrawal and y before the deposit, and "reads an inconsistent state where the total balance is 60." The reporting transaction wrote nothing, yet its result is wrong.

How isolation levels help

Berenson and colleagues open their paper with the purpose of isolation levels: "Running concurrent transactions at different isolation levels allows application designers to trade throughput for correctness." Each level is a promise about which of the patterns above the database will refuse. The SQL standard names four levels and defines the lower three by which of three phenomena each must prevent: dirty read, non-repeatable read and phantom. PostgreSQL's manual prints the standard's table with one extra column.

Read it from the bottom up. Each step up the ladder forbids one more pattern. Read Committed stops you from seeing data that was never committed. Repeatable Read also stops a row from changing under you mid-transaction. Serializable also stops phantoms. The fourth column, "Serialization Anomaly," is the one that matters for this report's question: it is "Possible" at every level except Serializable. A lost update or a write skew is a serialization anomaly. "Allowed, but not in PG" marks places where PostgreSQL is stricter than the standard requires.

The standard's list is incomplete

Preventing the three named phenomena does not make execution serializable. Berenson and colleagues showed with exact histories that the standard's English definitions are ambiguous, that dirty writes and lost updates fall outside them, and that a history like H1 can avoid the strictly worded phenomena and still be wrong. That is why their version of the standard's table labels its top row "ANOMALY SERIALIZABLE" rather than "SERIALIZABLE." Their fuller table adds the missing patterns as columns.

Read across the Read Committed row: lost update, read skew and write skew are all "Possible," and that is the default level in PostgreSQL. Then compare the Repeatable Read and Snapshot rows. Each misses something different, phantom in one and write skew in the other, so neither is simply stronger. Only the bottom row says "Not Possible" in every column.

Two ways a database enforces a level

Databases implement these promises in two main ways. In a locking database, a transaction must take a shared lock to read a row and an exclusive lock to write it, and a conflicting request waits. Berenson and colleagues show that in such a system the levels differ mainly in how long read locks are held. Write locks are always held until commit. Read Committed releases each read lock right after the read, which is exactly the gap a lost update slips through. Repeatable Read holds read locks on rows until commit. Serializable also locks the search conditions themselves, so no new matching row can appear. Holding every lock until commit is called two-phase locking, and it gives serializability.

Many databases, including PostgreSQL, MySQL's InnoDB for plain SELECTs, and Oracle, instead keep old versions of rows. Each transaction reads a consistent snapshot of committed data, so, as the PostgreSQL manual says, "reading never blocks writing and writing never blocks reading." At Read Committed, each statement gets a fresh snapshot, so two SELECTs in one transaction can disagree. Under snapshot isolation, the whole transaction sees one snapshot taken at its first statement, and if two transactions write the same row, the second to commit is aborted. That rule is what stops the lost update. It cannot stop write skew, because the doctors wrote different rows. PostgreSQL's manual states that its Repeatable Read "is implemented using a technique known in academic database literature and in some other database products as Snapshot Isolation."

This diagram puts the levels in order of strength, with each line labeled by the pattern the stronger level removes. Follow the right-hand side: Snapshot Isolation removes lost update (P4) and read skew (A5A) relative to Read Committed, and the single line from it up to Serializable is labeled A5B, write skew. That one pattern is all that separates snapshot isolation from full correctness, and it is the one the doctors example exhibits.

A level's name tells you less than its tested behavior.

Defaults are usually weak

Most databases do not run serializable unless you ask. PostgreSQL 18's manual says "Read Committed is the default isolation level in PostgreSQL," and MySQL 8.4's says the InnoDB default is Repeatable Read, which by the table above still allows lost updates. A 2013 survey found the pattern was broad.

Only 3 of the 18 defaulted to serializable, and 8 did not offer it at all; Oracle 11g's strongest level was snapshot isolation. The product versions are old and some products are gone, so use the table for the pattern, not for any one database's current setting.

The price of stronger isolation

A stronger level does not make conflicting transactions compatible. It stops them, in one of two ways. A locking database makes one transaction wait for the other. A snapshot database lets both run and then aborts one with a serialization failure. In PostgreSQL that error carries SQLSTATE 40001, and the manual is direct about the consequence: "Applications using this level must be prepared to retry transactions due to serialization failures." Retrying means rolling back and running the whole transaction again from its first read, so that it decides on fresh data.

The PostgreSQL manual gives a second write-skew example with numbers you can check. A table holds rows with class 1 values 10 and 20, and class 2 values 100 and 200. Transaction A sums class 1 (30) and inserts that sum as a class 2 row; transaction B sums class 2 (300) and inserts that as a class 1 row. At Repeatable Read both commit. At Serializable one is rolled back with "could not serialize access due to read/write dependencies among transactions," because, as the manual explains, "if A had executed before B, B would have computed the sum 330, not 300." That error is what the help from an isolation level looks like: a refusal the application must handle, not a silent fix.

How much the stronger level costs depends on how it is built and on the workload. Ports and Grittner measured PostgreSQL's Serializable mode against snapshot isolation and against classic locking (strict two-phase locking, S2PL).

The y-axis is throughput as a fraction of snapshot isolation's. The blue Serializable line stays near the top; the authors report a cost of "less than 7% relative to snapshot isolation." The red locking line falls to under half of snapshot throughput when most transactions only read, because readers must wait on writers' locks. On an auction-site benchmark, Serializable handled 422 requests per second against snapshot isolation's 435, while locking managed 208. These are one study's numbers on 2012 hardware, PostgreSQL 9.1 and a locking implementation the authors wrote for comparison, so they show that serializability can be cheap, not that it always is.

What isolation cannot fix

These failures are not only theoretical, and they are usually silent. Ports and Grittner note that such anomalies "typically manifest themselves as silent data corruption": no error, just wrong data found later. ACIDRain quotes the Bitcoin exchange Flexcoin, which closed in 2014 after an attacker, "by sending thousands of simultaneous requests," moved coins between accounts "until the sending account was overdrawn, before balances were updated." The researchers then tested 12 popular e-commerce platforms and confirmed 22 vulnerabilities, including reusing a gift card and corrupting inventory.

The table splits the 22 into two kinds. Five depended on the isolation level: they worked at every database's default and disappeared at serializable (one survived on the two databases whose maximum is snapshot isolation). The other 17, the "Remaining" column, survive at every level, because the application never put the related steps in one transaction. A database can only isolate what you group together. If the SELECT and the UPDATE run as separate transactions, no isolation setting can make them atomic. This answers the most likely misreading of "isolation levels help": raising the level protects only the logic inside a transaction.

At weaker levels, an application can still close specific gaps on purpose. Ports and Grittner list the usual tools, and the PostgreSQL manual and ACIDRain show them in use:

  • Do the arithmetic in one statement, such as UPDATE … SET balance = balance - 99 WHERE id = … AND balance >= 99, so no stale value passes through application code.
  • Lock the rows you read with SELECT … FOR UPDATE, so a second transaction waits before reading them. In the doctors case, the lock must cover the rows being counted, not only the row being changed.
  • Turn a hidden conflict into a real one, for example by having both transactions update a shared row that represents the rule, so ordinary write locks collide.
  • Let the database enforce the rule with a constraint, so an invalid commit fails no matter how it was interleaved.

Each tool fixes one known pattern, which means someone must find every pattern. Ports and Grittner's motivating case, the Wisconsin court system, had hundreds of tables and more than twenty programmers, which made checking every pair of transactions for conflicts impractical. That is the case for running Serializable and handling retries instead.

Finally, a guarantee is only as good as its implementation. In 2020 Jepsen found that PostgreSQL's Serializable mode could miss a conflict in a rare three-transaction case. The 12.4 release notes describe the fix: the bug "could allow a serializable transaction to commit when it should have failed with a serialization error." It is fixed, but the lesson holds. Test suites like Hermitage and Jepsen can show that an anomaly happens, never prove that it cannot, so the strongest evidence about your database is still the documented, tested behavior of the version you actually run.
