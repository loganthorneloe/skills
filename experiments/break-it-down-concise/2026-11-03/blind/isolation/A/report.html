Database transaction isolation.

Sources

A Critique of ANSI SQL Isolation Levels↗

Hal Berenson, Phil Bernstein, and colleagues · Conference paper and Microsoft Research technical report, ACM SIGMOD · June 1995

The reference analysis of what the SQL standard's levels guarantee. Its authors include Jim Gray, who won the Turing Award for transaction processing, and Jim Melton, editor of the SQL standard. They prove, step by step, which interleavings each level allows. The proofs still hold; its notes on 1995 products are dated.

PostgreSQL 18 Documentation: Transaction Isolation↗

The PostgreSQL Global Development Group · Official product documentation, postgresql.org · Current manual, accessed November 2026

The developers' own statement of what each level does in the current release, with SQL examples and the errors applications receive. It describes PostgreSQL only.

Serializable Snapshot Isolation in PostgreSQL↗

Dan R. K. Ports and Kevin Grittner · Conference paper, Proceedings of the VLDB Endowment (VLDB 2012) · August 2012

By the two engineers who built PostgreSQL's Serializable mode. It explains why snapshot isolation falls short and measures the stronger mode's cost on 2012 hardware, one example rather than a general rule.

Hermitage: Testing Transaction Isolation Levels↗

Martin Kleppmann and contributors · Open test suite and results, GitHub · First published November 2014, updated January 2026

Rerunnable two-session scripts that try to trigger each anomaly, with results comparing what each product's level is called and what it prevents. Tests ran by hand on particular versions, some old, and can show an anomaly but not prove its absence.

ACIDRain: Concurrency-Related Attacks on Database-Backed Web Applications↗

Todd Warszawski and Peter Bailis · Conference paper, ACM SIGMOD · May 2017

Stanford researchers confirmed 22 exploitable concurrency bugs in 12 popular e-commerce platforms by triggering each against the real software, and sorted which ones a stronger level would stop.

The short answer

A database runs many transactions at once and interleaves their steps. If one transaction reads a value, and another changes that value before the first finishes, the first acts on stale data. Each transaction did the right thing for the data it saw, yet the combined result matches no order of running them one at a time. Isolation levels tell the database which of these interleavings to forbid. Weaker levels forbid fewer and run faster. Only Serializable forbids all of them, by making transactions wait or cancelling one for the application to retry.

What "correct" means

A transaction is a group of SQL statements, between BEGIN and COMMIT, that the database treats as one unit. Each transaction is written to keep the data's rules, called invariants: a balance never goes below zero, or at least one doctor is on call. A transaction is correct if it keeps those rules when it runs alone.

That gives a test for running several at once: if every transaction is correct alone, running them one after another, in any order, is also correct. Berenson and colleagues call a concurrent run serializable when its result "is equivalent to a serial history", meaning some one-at-a-time order. Serializability is the reference definition of correct concurrent behavior. Every problem below is a way of falling short of it.

How two correct operations go wrong

Most of these bugs follow one pattern: read a value with SELECT, decide or compute something in application code, then UPDATE based on what was read. The ACIDRain paper opens with a withdrawal function written this way.

Run alone, panel (a) never overdraws. Run twice at once, both calls read $100 before either writes, and $198 leaves an account holding $100. Notice the caption's warning about panel (b): wrapping the steps in a transaction is not enough at Read Committed or weaker unless the read also locks the row. Grouping the steps is necessary; the isolation level decides how well the group is protected.

The same race on a deposit is called a lost update. Berenson's example starts with x = 100. One transaction adds 30 and another adds 20; run in either order, x ends at 150. Interleaved, both read 100, one writes 120, the other writes 130, and the paper notes the final value "contains only the increment of 30." Hermitage reproduces it in PostgreSQL with two sessions on a table holding the value 10:

begin; set transaction isolation level read committed; -- T1
begin; set transaction isolation level read committed; -- T2
select * from test where id = 1; -- T1
select * from test where id = 1; -- T2
update test set value = 11 where id = 1; -- T1
update test set value = 11 where id = 1; -- T2, BLOCKS
commit; -- T1. This unblocks T2, so T1's update is overwritten
commit; -- T2

Each session meant to add one, so the right answer is 12. The value ends at 11. The bug needs the new value to be computed in the application; PostgreSQL's manual explains that a single UPDATE ... SET balance = balance + 100 at Read Committed waits for the other writer and then re-applies to the committed row, so it loses nothing.

The general cause is a conflict: two transactions touch the same data, at least one writes it, and one acts on a value the other changes before it finishes. Named patterns describe particular conflicts. A dirty read uses data another transaction has not yet committed. A non-repeatable read gets different values from the same row twice. A phantom is a repeated search that finds a different set of rows.

Isolation levels as a ladder

The SQL standard names four levels: Read Uncommitted, Read Committed, Repeatable Read, and Serializable. It defines each lower level by which of three phenomena it must prevent: dirty reads, non-repeatable reads, and phantoms. Berenson and colleagues showed that list has holes. Lost updates and write skew fall outside it, and preventing all three still does not guarantee a serializable result. Their Table 4 gives the fuller picture.

Read down the table and each step forbids more: Read Committed stops dirty reads, Repeatable Read also stops lost updates and values shifting mid-transaction. Snapshot isolation gives each transaction a consistent copy of the data as of its start and refuses the second of two writes to the same row. It blocks lost updates, but write skew (A5B) remains "Possible." Only the Serializable row reads "Not Possible" in every column. The Repeatable Read row is the paper's locking definition; products differ from it.

Why snapshots are not enough

Write skew happens when two transactions read overlapping data, each checks a rule, and each then writes a different row. Ports and Grittner's example has two doctors on call and a rule that at least one stays.

Each transaction counts two doctors and takes one off call. Either order alone leaves one on duty; under snapshot isolation both commit and nobody is. The authors explain why row locks do not help: "the two transactions modify different rows and thus do not conflict." Only Serializable, or an explicit SELECT ... FOR UPDATE on the rows counted, stops it.

The price, and the names

Stronger levels prevent anomalies by making a transaction wait or by cancelling it. PostgreSQL's manual tells applications at its stronger levels to "be prepared to retry transactions due to serialization failures." A rerun reads the committed value, so the result matches a one-at-a-time order.

The cost depends on enforcement. Ports and Grittner measured PostgreSQL's Serializable mode at under 7% slower than snapshot isolation, while a classic locking version ran at under half the throughput on read-heavy workloads. That is one 2012 study.

Level names also mislead. PostgreSQL defaults to Read Committed, and its Repeatable Read is snapshot isolation, so it refuses lost updates. Hermitage found that MySQL's default Repeatable Read still allows lost updates, and that Oracle's "serializable" is snapshot isolation. A level's name does not tell you what it prevents.

What isolation cannot fix

Isolation protects only the steps inside one transaction. Of ACIDRain's 22 vulnerabilities, 5 came from weak default levels, and 17 came from code that never grouped its steps into a transaction, which no level can repair. At weaker levels, applications close specific gaps themselves: single-statement updates, SELECT ... FOR UPDATE, and constraints the database enforces. And a guarantee is only as good as its implementation; testing can expose a broken one but not prove one holds.
