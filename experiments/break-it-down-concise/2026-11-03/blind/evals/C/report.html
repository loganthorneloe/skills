AI application evals, from first principles.

Sources and how far to trust them

Demystifying evals for AI agents↗

Mikaela Grace, Jeremy Hadfield, Rodrigo Olivares, and Jiri De Jonghe · Engineering blog post, Anthropic · January 2026

Engineers who build and grade agents in production describe what works for them. It is experience, not a controlled study.

τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains↗

Shunyu Yao, Noah Shinn, Pedram Razavi, and Karthik Narasimhan · Research paper, arXiv preprint (ICLR 2025) · June 2024

The authors built simulated retail and airline support desks and measured repeated runs of the same requests. The models are from 2024, the customers are simulated, and the authors have since corrected the original tasks, so read its numbers as a pattern, not current scores.

Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena↗

Lianmin Zheng, Wei-Lin Chiang, and colleagues · Research paper, NeurIPS 2023 Datasets and Benchmarks · June 2023

An experiment comparing model verdicts with about 3,000 expert votes, plus tests for bias. It used 2023 models on general chat questions, so it shows judges can be useful and biased, not how one will grade your bot.

Your AI Product Needs Evals↗

Hamel Husain · Practitioner blog post, hamel.dev · March 2024

The engineer who built the eval system for a deployed assistant describes it with real checks. It is one self-reported case, and the author sells an evals course.

The short answer

A model can answer the same question differently each time, and a prompt change that fixes one conversation can quietly break another, so “I tried it and it looked fine” tells you little. An eval is a repeatable test set: realistic inputs, each with a rule for success, run several times and scored automatically. For a support assistant, start with 20 to 50 real conversations that went wrong, write down what should have happened, and check outcomes with code wherever you can.

Why ordinary testing is not enough

A model’s reply is sampled: it picks each next word with some randomness, so the same input can produce different wording, decisions, or tool calls. Ordinary tests assume the same input gives the same output.

The prompt also couples everything. One instruction governs every conversation, so an edit for angry customers can change how refunds go. Husain saw this on a real assistant: fixing one failure “led to the emergence of others,” with no view of quality “beyond vibe checks.” Without fixed tests, you cannot tell a regression from random variation.

A running example: a customer writes “My mug arrived cracked, order 1042, I want my money back.” Your assistant can look up orders and issue refunds. It should refund the $18, say what happens next, and promise nothing your policy forbids.

What an eval is made of

Anthropic’s vocabulary separates the decisions. A task is one test case: an input plus success criteria, such as the mug message plus “refund of $18 issued.” A trial is one run of it; you run several because outputs vary. A grader scores a trial. The transcript records every message and tool call, and the outcome is the state afterward, such as whether a refund row exists in your database. A suite is a set of tasks, for example refunds, cancellations, and escalations.

Grading reads both the transcript and the outcome, because a bot can say “your refund is on its way” when no refund exists. The diagram’s task is a coding fix, but the mug task has the same shape.

Three ways to grade, cheapest first

Code graders are ordinary assertions. Was the refund tool called with $18 or less? Did the reply leak internal IDs? Husain’s team enforced one prompt rule with a regex that fails any reply containing a database UUID. Such checks are fast, free, and exact, but cannot judge tone or clarity.

For those, a second model grades the reply against a narrow rubric; this is an LLM judge. Anthropic suggests one question per quality and letting the judge answer “unknown” rather than guess. A judge is flexible, but it is a model whose accuracy you must measure.

Zheng and colleagues showed judges two similar answers, then the same pair in reverse order. In the Consistency column, the best 2023 judge, GPT-4, kept its verdict only 65% of the time, and Claude-v1 with the default prompt favored the first answer in 75% of cases. The pairs were deliberately near-identical, so real cases flip less. The same study found GPT-4 agreed with expert graders 85% of the time, slightly above the 81% at which the experts agreed with each other. A judge can match a person and still have systematic quirks, so Husain has a domain expert label 25 to 50 examples and revises the judge’s prompt until its labels match.

Human review is the third grader and the reference for the other two; it is too slow to grade every run.

Why you run each task more than once

If the mug task passes 75% of the time, the chance that three customers in a row are served correctly is 0.75³, about 42%. This is pass^k: the chance that all k tries succeed. It fits a support bot, where each customer gets one try. Its mirror, pass@k, asks whether at least one of k tries succeeds, which suits tools where you can retry.

Each model’s two lines start at its average success, then split. Solid lines fall because the same model on the same tasks passes some runs and fails others, with only sampling randomness changing. gpt-4o succeeded on more than 60% of retail tasks on average, but its pass^8 fell below 25%: the chance of succeeding in all eight runs was under one in four. One test run would have hidden that. Today’s models score differently; the method carries over.

Starting with your support assistant

Anthropic’s advice is that “20-50 simple tasks drawn from real failures is a great start,” because early changes have large effects a small set can detect.

  1. Pull conversations that went wrong from your support queue, bug reports, and manual testing. Each becomes a task.
  2. Write each task’s starting account state and what must be true at the end, precisely enough that two support staff would agree on pass or fail.
  3. Include cases where the bot should refuse, such as a refund outside the return window.
  4. Check outcomes with code; add a judge only for what code cannot see.
  5. Run each task several times on fresh test data and read the failed transcripts.

In plain Python, with run_assistant and call_model standing for your application and API wrapper:

from math import comb

TASKS = [
    {"id": "refund-damaged-mug",
     "message": "My mug arrived cracked. Order 1042. I want my money back.",
     "start": {"orders": {"1042": {"status": "delivered", "total": 18.00, "days_ago": 6}}},
     "expect": {"refund_issued": True, "refund_amount": 18.00}},
    {"id": "refund-outside-window",
     "message": "I'd like a refund for order 0877.",
     "start": {"orders": {"0877": {"status": "delivered", "total": 40.00, "days_ago": 400}}},
     "expect": {"refund_issued": False}},
]

def code_checks(task, result):
    """Exact checks on the final state and the reply. Cheap; run on every change."""
    problems = []
    for key, want in task["expect"].items():
        got = result["final_state"].get(key)
        if got != want:
            problems.append(f"{key}: expected {want}, got {got}")
    if "internal note" in result["reply"].lower():
        problems.append("leaked internal note")
    return problems

def judge(task, result):
    """One narrow question a second model answers: pass, fail, or unknown."""
    prompt = ("Grade this customer-support reply. Answer only pass, fail, or unknown.\n"
              "Pass only if it tells the customer clearly what happens next.\n\n"
              f"Customer: {task['message']}\nReply: {result['reply']}")
    return call_model(prompt).strip().lower()

def pass_hat_k(n, c, k):
    """Chance that k fresh runs all pass, given c passes out of n (τ-bench estimator)."""
    return comb(c, k) / comb(n, k)

N = 5
for task in TASKS:
    passes = 0
    for _ in range(N):
        result = run_assistant(task["message"], task["start"])   # fresh test data each run
        if not code_checks(task, result) and judge(task, result) == "pass":
            passes += 1
    print(task["id"], f"{passes}/{N} passed", "pass^3 =", round(pass_hat_k(N, passes, 3), 2))

Reading failures is where you learn most. Of 40 failed gpt-4o retail conversations in τ-bench, 4 were the test’s fault, a typo or ambiguous instruction. The other 36 sorted into a few kinds.

“Wrong argument” is the right action with a wrong detail, such as the wrong product option. “Wrong info” gives the customer a wrong or missing fact, such as a wrong total. “Wrong decision” misapplies a store rule. “Partially resolve” stops early, fixing one order’s address when the customer asked for all. Each kind points to a different fix and new tasks. This is one model in one simulated store, but the practice transfers: label failures, count them, fix the largest group first.

What evals cannot tell you

An eval measures only the cases you wrote, so Anthropic pairs it with production monitoring and transcript reading. The eval can be wrong too: graders reject valid answers, and τ-bench’s own authors later replaced its tasks with fixed versions. The pass rate you require is a product decision about which failures you tolerate. What evals buy is the ability to change a prompt or model and know what improved and what broke before customers find out.
