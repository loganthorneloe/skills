## Gaps list

- C1: only conditional/implicit sources beyond Berenson §2.1 — Berenson's definition ("A transaction groups a set of actions that transform the database from one consistent state to another") passes; no gap in substance, it is textbook background.
- C11: Oracle behavior rests on Hermitage (tested on an older Oracle release) plus Ports & Grittner (2012) and HAT (2013); no current Oracle documentation read — state Oracle as "per Hermitage's tests" rather than as current fact.
- C12: cross-vendor defaults survey is historical (January 2013); current defaults verified only for PostgreSQL 18 (READ COMMITTED) and MySQL 8.4 (REPEATABLE READ); Hermitage stars give defaults for the others at tested versions.
- C14: only one benchmark source (Ports & Grittner, 2012 hardware, PostgreSQL 9.1); no current or cross-vendor measurement. Present as one measured example, not a general cost.
- C15: Flexcoin mechanism rests on the exchange's own statement as quoted by ACIDRain; independent technical write-up inaccessible.
- C17: Jepsen analysis read only via summary — inaccessible full text for verbatim quotes.
- Disputed premise: the question's phrase "how isolation levels help" can suggest that raising the level fixes concurrency bugs generally. ACIDRain shows 17 of 22 real bugs came from operations not grouped into one transaction, which no isolation level can repair; isolation only protects what is inside a transaction.
- Definitions conflict (not a gap but a caveat): there are two definitional frameworks — the SQL standard / Berenson phenomena (P0–P4, A5A/B) and Adya's dependency-cycle phenomena (G0, G1, G2, used by Hermitage). Their names map roughly (G2-item ≈ write skew, G-single ≈ read skew) but not one-to-one; writers should pick one vocabulary for the reader and note the other exists.

## Draft reader-facing entries (passing and conditional sources)

### A Critique of ANSI SQL Isolation Levels
*Hal Berenson, Phil Bernstein, and colleagues · Conference paper and Microsoft Research technical report, ACM SIGMOD · June 1995*

This is the paper that pinned down what the SQL standard's isolation levels actually guarantee. Its authors include Jim Gray, who won the Turing Award for transaction processing, and Jim Melton, editor of the SQL standard. They write out exact sequences of reads and writes and show which ones each level lets through. The paper proves that the standard's plain-English rules leave holes: lost updates, dirty writes, and write skew all slip past them, and blocking the three named problems still doesn't make execution equivalent to running transactions one at a time. It also gave the first precise definition of snapshot isolation, which many databases now use. Its arguments are logical proofs, not measurements, so they still hold. Its descriptions of specific 1995 products don't describe today's versions. Later researchers (Adya and colleagues, 2000) reworked its definitions so they don't assume locking. The newer vocabulary used by testing tools comes from that rework.

### PostgreSQL 18 Documentation: Transaction Isolation
*The PostgreSQL Global Development Group · Official product documentation, postgresql.org · Current manual, accessed November 2026*

The developers of PostgreSQL wrote this page to say exactly what each isolation level does in the current release. It lays out the standard's four levels in a table, gives short SQL examples of what goes wrong at each one, and shows the error a transaction gets when the database refuses a conflicting interleaving. It also confirms three facts about PostgreSQL: Read Committed is the default, Repeatable Read is really snapshot isolation, and Serializable works by detecting conflicts and aborting one transaction, which the application must then retry. It describes only PostgreSQL. Other databases use the same level names for different behavior.

### MySQL 8.4 Reference Manual: Transaction Isolation Levels
*Oracle Corporation · Official product documentation, dev.mysql.com · MySQL 8.4 manual, accessed November 2026*

MySQL's own manual for its main storage engine, InnoDB, in the current long-term-support release. It confirms that the default level is Repeatable Read. It also explains why that level behaves unexpectedly: plain SELECTs read from a snapshot taken at the start, while UPDATEs and locking reads act on the newest committed data. The manual itself warns that these two views can be "inconsistent with each other." The vendor describes the default as strongly consistent, but independent tests (Hermitage, ACIDRain) found it lets lost updates through. Read this manual alongside those tests.

### Serializable Snapshot Isolation in PostgreSQL
*Dan R. K. Ports and Kevin Grittner · Conference paper, Proceedings of the VLDB Endowment (VLDB 2012) · August 2012*

The two engineers who built PostgreSQL's Serializable mode describe how it works and measure what it costs. Grittner needed it at the Wisconsin court system, where silent data corruption in warrant records was unacceptable. The paper uses a simple example of two doctors who each take themselves off call: snapshot isolation lets both commit, which leaves no one on call. It shows the cycle of dependencies that makes this impossible in any one-at-a-time order and explains how the database detects that pattern and aborts a transaction. In their benchmarks, serializable mode ran within about 7% of snapshot isolation, while traditional locking was far slower on read-heavy workloads. Those numbers come from 2012 hardware, PostgreSQL 9.1, and a locking implementation the authors built themselves for comparison, so treat them as one measured example. In 2020 an independent tester found a bug in this mechanism, and it has since been fixed.

### Highly Available Transactions: Virtues and Limitations
*Peter Bailis, Aaron Davidson, and colleagues · Conference paper (extended version), VLDB 2014 / arXiv · February 2013*

We use one table from this paper: a survey of the default and strongest isolation levels in 18 databases as of January 2013. Only 3 of the 18 ran serializable by default, and 8 didn't offer serializable at all. The authors are database researchers who compiled the table from vendor documentation. It is a historical snapshot of old product versions, and some of those products no longer exist. It supports the general point that weak defaults are normal, a point the current PostgreSQL and MySQL manuals still confirm. It does not show any particular database's current default.

### ACIDRain: Concurrency-Related Attacks on Database-Backed Web Applications
*Todd Warszawski and Peter Bailis · Conference paper, ACM SIGMOD · May 2017*

Stanford researchers tested whether real shopping software breaks when an attacker sends many requests at once. They found and confirmed 22 such vulnerabilities in 12 popular e-commerce platforms. The bugs let attackers spend a gift card repeatedly, get items for free, or corrupt inventory counts. Five came from the database's default weak isolation level. The other 17 came from code that never grouped its steps into one transaction, which no isolation level can fix. The paper also recounts the 2014 Flexcoin Bitcoin exchange, which closed after an attacker exploited a race between transfers. The "2 million websites" figure counts sites running the affected software, not sites that were attacked. Some attacks needed an added network delay to trigger reliably.

### Hermitage: Testing Transaction Isolation Levels
*Martin Kleppmann and contributors · Open test suite and results, GitHub · First published November 2014, updated January 2026*

Kleppmann, author of *Designing Data-Intensive Applications*, wrote this suite of tests. Each test is a step-by-step script for two database sessions that tries to trigger a specific concurrency anomaly. Anyone can rerun the scripts, so the results can be checked rather than taken on trust. Its summary table compares what each database's level is called with what it actually prevents. The results show that the names don't line up across products: "repeatable read" is snapshot isolation in PostgreSQL, but in MySQL it still allows lost updates. The tests were run by hand on particular versions, some of them old (the PostgreSQL scripts used 9.3.5). They can show that an anomaly occurs but cannot prove it never will, and they say nothing about speed. The PostgreSQL results agree with the current manual.

### Jepsen: PostgreSQL 12.3 (with PostgreSQL 12.4 release notes)
*Kyle Kingsbury · Independent consistency analysis, jepsen.io · June 2020; PostgreSQL Global Development Group release notes, August 2020*

Jepsen is an independent tester that runs automated workloads against databases and checks the results against formal definitions. In 2020 it found that PostgreSQL's Serializable mode could, in a rare case involving three concurrent transactions, let through an anomaly it should have blocked. The bug dated back to 2011. The PostgreSQL project fixed it in its August 2020 releases, and the release notes describe the fix. A database's isolation guarantee is only as good as its implementation. The bug is fixed and doesn't describe current behavior. We read the Jepsen report only in summary, so we quote the release notes rather than Jepsen directly.
